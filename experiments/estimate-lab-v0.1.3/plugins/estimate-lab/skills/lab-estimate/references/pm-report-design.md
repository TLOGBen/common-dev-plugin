# PM 確認報告設計

生成或檢查 `assessment-report.html` 時讀取。這份報告只有一個任務：讓 PM 用最短時間逐項確認「改什麼、為何是這些人天、哪個主動發現改變了原先判斷」。技術完整性保留，但不占據第一層閱讀動線。

## 閱讀順序

固定使用下列資訊層級：

1. 本次摘要：把 `outcome.pmCurrentState`、`goal`、`responsibilityBoundary` 合成同一個閱讀區，直接說目前能沿用什麼、哪裡真的要改、要達成什麼與尚需誰提供什麼；不逐項傾倒版本、class、套件與搜尋命中。
2. 評估項目與人天：每列同時顯示成果名稱、原 `externalSummary`、低／基準／高人天，讓 PM 不開細節就能比較。
3. 折疊技術附錄：採用方案、成果成立條件、關鍵依賴與技術證據收在同一個附錄入口。

`estimationReview.criticalFindings` 不另設全域主段；只放進所屬成果包的 dialog，讓 PM 在該項修改與人天的上下文中理解。

報告不要出現「白話版」「給 PM 的簡化版」等自我標籤。段落直接命名為「現況結論」「修改重點」「人天怎麼算」「主動發現」，文字本身使用 PM 可轉述的日常動詞。

## 直接陳述，不用文字表演

PM-facing 文字要直接傳達判斷。文字表演會用比喻或華麗措辭取代準確說法，讓讀者多花力氣解碼，也會帶入作者沒有選擇、無法控制的聯想。只要有準確的字面說法，就使用字面說法。例如，寫「一個值得調整的參數」，不要寫「一個值得轉動的旋鈕」；寫「這一點仍然重要」，不要寫「這一點證明自己值得保留」。

技術文也遵守這項規則。面向 PM 的句子不可先堆入 class、package、API、搜尋命中數與實作機制，再把結論留到句尾。固定順序是：

1. 先說結論。
2. 接著說影響範圍與人天。
3. 說明 PM 必須注意或決定的事項。
4. 把技術機制與證據移到表格或可展開技術層。

技術名詞只有在刪除後會失去精確意思時才保留，第一次出現時要解釋。例如，先說已確認的施工範圍與人天，再說尚未逐名確認的落點及其上限；搜尋命中數只表示查找範圍，不直接計價。技術分類與查詢方式放進可展開層。案件資料若只提供內部代稱，第一次出現時補上完整名稱或功能。

編輯每一句 PM-facing 文字時依序檢查：

1. 比喻或華麗措辭能否換成字面說法？
2. 讀者是否先看到結論，再看到技術機制？
3. 每個數字是否說明計數對象，以及它是否影響計價？

任一題未通過，就重寫該句，或把細節移到表格或可展開技術層。

## 成果包下鑽契約

每個 `clientPackage` 在第一層顯示成果名稱、原對外摘要與低／基準／高人天。整列使用 button 開啟原生 `<dialog>`：桌面為右側詳情抽屜，窄螢幕為全螢幕；頂部固定提供關閉，底部固定提供「回到評估項目」，Escape 與點擊 backdrop 也可關閉。關閉後焦點回到原按鈕，並維持頁面捲動位置。

巢狀工作集合要能用鍵盤展開與收合，不能把 summary 的鍵盤啟動誤認為點擊 backdrop。實際測焦點、Enter／Space 與 Escape，不以靜態 HTML 存在推定互動可用。

展開後依序顯示：

1. 原項目說明、低／基準／高人天、為什麼要做與怎麼完成。
2. 與本包相連的主動發現及其處理紀錄；按目前案件狀態辨識仍待承諾與已接受的事項，沒有就不顯示空白章節。
3. 該包下每個 work item 的 `pmChangeSummary`，80～160 字，說明實際改法、數量驅動與完成結果。
4. `changeTargets.pages`、`changeTargets.apis`、`changeTargets.files` 三張完整清單。標題自動顯示筆數；寫「六個畫面」時清單必須真的列出六個名稱。尚未逐項確認的總數不能偽裝成正式明細，應回到盤點補清單或留在阻擋估算的未知。
5. 依 `detailCatalogIds` 投影巢狀工作集合：direct-touch 顯示「逐項處理」表格及計價角色；generated 顯示「重新產製」的來源、方法與核對，明說不是 N 次人工修改；evidence-only 顯示「範圍證據」。generator 不掃 repository，也不建立第二份清單。
6. `pricingUnits × unitDays.baseline`、基準開發／測試拆分，以及 `baselineRationale`。每個基準單價都要說明包含哪些理解、修改、除錯與驗證，不能只寫「工程師估算」。
7. 低／基準／高的整包解釋：低值成立條件、基準公式為何代表目前最可能、高值吸收哪些同範圍風險。

頁面、API 或檔案確實不涉及時保留 0 筆並說明原因，不以空白造成漏列疑慮。檔案使用 repository-relative path；本機絕對路徑與客戶敏感資料仍由外部輸出去識別規則移除。

## 什麼才算主動發現

`estimationReview` 先反證目前的施工樣態與乘數，再保存結論。`criticalFindings` 只收「需求或人工初判未提到，而且會改變範圍、方案、責任、人天或驗收」的發現：

- **範圍落差**：需求初看是 4 個功能，沿共用元件、入口與流程追查後實際有 6 個修改或驗證面。
- **可行路線落差**：需求只說升版，但承重套件在目標版本需改採維護分支、替換元件或改寫關鍵行為。
- **計價模型落差**：原先以為共用一次，證據顯示每頁、每 API 或每個例外都要獨立施工；反向發現可批次處理、應降低乘數時也要列出。
- **責任或驗收落差**：成功依賴客戶環境、第三方端點或資料核對，而原範圍沒有承接者。

每張主動發現的標題先直接說結論。可見內容依序顯示 `estimateImpact`（人天怎麼看）與 `treatment`（PM 現在要注意什麼）。`statedAssumption`（原本怎麼算）、`evidenceConclusion`（後來查到什麼）與 `whyItMatters`（為什麼重要）依序收進「查看判斷依據」；技術名詞與長清單再下沉到該 work item 的工作集合。主動發現用 `clientPackageIds` 與 `evidenceIds` 連回成果包及證據。範圍落差另以 `scopeDelta` 保存比較對象、人工初判數、證據確認數、落點類別與 work item；證據確認數必須等於所連逐名清單筆數，不一致就阻擋 Gate 5、回到 discovery 重建清單。

若沒有 critical finding，仍需在 `conclusion` 說明反證結果，並以 `checkedPatterns` 列出實際檢查過的替代解釋；不能以空陣列假裝完成主動盤點。

核准或交付完成後，`treatment` 改標「原評估處理紀錄」，並保留原文及狀態脈絡；其中過去的 Gate 5 提醒不再包裝成新的 PM 待辦。不要因此抹除原紀錄，也不要推定部署、UAT 等後續條件已完成。

## 圖解與前端選擇

Estimate 內建適合本報告的 editorial SVG 能力。方法參考 [Diagram Design](https://github.com/cathrynlavery/diagram-design) 的低密度與可存取 SVG 原則，並以 [Anthropic frontend-design](https://github.com/anthropics/claude-code/blob/main/plugins/frontend-design/skills/frontend-design/SKILL.md) 檢查主題、資訊層級、文案與互動是否服務頁面的單一任務。

- 一張圖只回答一個明確問題。沒有 `clientPackage.visuals` 就完全不畫；只有圖比相鄰文字或清單更快說清關係時才保留，單包上限三張。
- 目標密度約 4/10，3～7 個節點，只有一個焦點色；無陰影、不靠裝飾性動畫營造「技術感」。
- 使用 4px 格線、明確層級與可列印的 inline SVG。每張 SVG 具有 `role="img"`、唯一 `aria-labelledby`、第一個子節點 `<title>` 與能說明內容的 `<desc>`。
- 依資料關係選工具：少量流程與比較直接使用 inline SVG；大量可篩選節點、網路或敏感度曲線可用 D3；三維空間本身承載意思時可用 Three.js。
- 動畫只在「先後順序本身會改變理解」時使用；完整靜態畫面必須先成立，並尊重 `prefers-reduced-motion`。
- 顏色、編號、標籤與結構只在傳達真實狀態、數量或關係時使用。畫面文字用主動語態，控制項名稱與展開後結果一致。

## 驗收

- 只看第一層時，fresh reader 能說出本案成果、現況、責任邊界，並直接比較每包低／基準／高值與應優先點開哪包。
- 點開任一成果包後，能逐項回答有哪些頁面、API、檔案，基準值如何重算，低／基準／高差在哪裡。
- 主動發現只出現在相關成果包 dialog；關閉 dialog 後焦點與捲動位置回到原列，可立即繼續比較下一項。
- 「N 個頁面／API／檔案」與清單實際筆數相等；未確認的名稱不以約數冒充完整清單。
- 桌面與窄螢幕皆可閱讀；鍵盤焦點可見；列印時展開內容不遺失。
- 用實際案件資料生成後截圖檢查。刪除不服務確認任務的裝飾；若圖表不比一段文字更快，就移除圖表。
