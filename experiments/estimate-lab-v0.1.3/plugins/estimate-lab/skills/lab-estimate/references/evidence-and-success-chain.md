# 證據與成果成功鏈

當 Gate 2 已確認成果大方向，需要判斷證據是否足夠、建立該方向下的 方案摘要，或從未知前進到可估算狀態時讀取。Gate 4 選定具體方案後，再將地圖收斂為該方案的完整成功鏈。

## 證據回答命題

每個證據先寫出它要支持或推翻的命題。檔案數量、搜尋命中、build success、HTTP 200 與 DB 連線各自只證明有限範圍；把證據能證明的命題和不能證明的部分一起記錄。

證據強度可使用：

- `runtime`：真實運行、DB、瀏覽器、API 或部署行為。
- `build`：固定輸入與環境下的編譯、測試或封裝結果。
- `static`：來源碼、設定、binary inspection 或可靠統計。
- `documented`：官方／客戶文件或責任方說明。
- `inferred`：由多項證據形成、仍需標示條件的推論。

## 從目的畫成功鏈

以選定方案的成果為終點，逐步回答：

1. 哪些能力必須存在，成果才成立？
2. 每項能力由誰負責，是否納入我方人天？
3. 依賴哪些前置、外部環境或客戶決定？
4. 用什麼證據可以確認完成？
5. 還有哪個未知會讓這個節點改變或拆分？

節點狀態使用 `done`、`working`、`needs-pm`、`fog`、`external`、`blocked`。地圖呈現 Frontier 是為了說明 Agent 正在解哪個問題，以及何時才需要 PM；它不是漂亮的進度動畫。

## 成功鏈收斂

地圖可進入估算前，至少滿足：

- 成果驗收條件能回到具體節點。
- 每個節點有 owner、estimate disposition、依賴與完成證據。
- `priced` 節點確實需要我方改動；`zero`／`external` 節點有清楚原因。
- 仍為 fog 的節點已解開，或有可用於條件式估算的合理上限。
- 重複視角已合併成同一能力節點。

地圖完成後才建立工作樣態。此時先不讀舊總數與舊費率，使新基線由成功鏈本身形成。

## 需要 PM 的時機

只有當技術事實已能把問題壓縮成業務保障、責任、範圍或費率取捨時，才把節點標成 `needs-pm`。問題應說清楚不同答案會改變哪個成功條件與人天；尚未完成的技術探索留在 Agent Frontier。
