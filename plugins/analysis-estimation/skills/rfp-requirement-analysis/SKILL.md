# RFP 需求分析（第一段）

把一份 RFP / 需求規格書，轉成兩組互相對照的交付物：

1. **需求分析報告**（單檔）：需求目的 / 拆包建議 / 模組清單 / 各模組功能 / Use Case 圖 / 主流程 Sequence / 對外連線 / 非功能需求。
2. **逐功能 API 與頁面操作分析**（一模組一檔 + 一份索引彙總）：把每個模組的每個功能展開成「目標 / API 表 / 頁面操作表」，並抽出跨模組共用 API、命名慣例、覆蓋檢查。

這兩組文件是後續「架構設計（第二段）」與「BDD 驗收規格（第三段）」的唯一輸入來源，所以**追溯性與覆蓋完整性**比文采重要：每個功能都要能往上對回 RFP 章節、往下被 API 與 BDD 引用。

## 為什麼這樣切

RFP 通常是幾十頁的散文 + 表格，業務功能藏在章節裡、非功能需求散在另一章、介接需求又在第三章。如果直接跳到寫 code 或畫架構，會漏功能、重工、或把橫切關注（簽核 / 稽核 / 遮罩 / 報表 / 介接）在每個模組重畫一遍。先做這一段，是為了得到一份**機械可比對的功能清單**，後面每一段都拿它當「對帳基準」做覆蓋檢查。

## 工作流程

### 步驟 0：定位輸入與輸出位置
- 找到 RFP 來源檔（PDF / docx / md）。PDF 用 Read 的 `pages` 參數分批讀完（超過 10 頁必填 pages，每次最多 20 頁），**務必讀完全文**，不要只讀前幾頁就推測。
- 預設輸出位置（除非使用者另指定）：
  - 需求分析報告 → 專案目錄下 `RFP分析_<系統名>.md`
  - 逐功能分析 → 專案目錄下 `功能API分析/`（`00-索引與彙總.md` + 每模組一檔 `NN-<模組>.md`）
- 開工前先跟使用者確認系統名稱、輸出資料夾、以及預設技術拆包（Vue 前端 / Spring Boot 後端，可覆寫）。

### 步驟 1：通讀並建模組骨架
讀完 RFP 後，先產出**需求分析報告**（用 `${CLAUDE_PLUGIN_ROOT}/skills/rfp-requirement-analysis/templates/需求分析報告.md` 當骨架填充）。重點：
- **模組清單表**要標 RFP 章節，作為後續對帳的錨點。
- **拆包建議**：預設拆前端包（Vue SPA）/ 後端包（Spring Boot），說明跨包契約（RESTful + 統一回應封套、AOP 處理 Logging/Security/個資遮罩）。
- **Use Case 圖、主流程 Sequence** 用 mermaid。把外部系統（eHR/SSO/會計/EIP/銀行…）畫成外部參與者。
- **對外連線表**：對象 / 方向 / 內容 / 備註，逐一列出每個介接。
- **非功能需求**：登入密碼、稽核日誌、個資保護、安控資安、資料模型、效能維運、批次排程、交付專案管理，逐項落地（不要只寫「符合資安要求」這種空話，要把 RFP 的具體數字與規則抄進來，例如密碼 ≥8 碼、稽核保留 ≥5 年、備援 3 小時回復）。
- 凡 RFP 文字模糊或需訪談確認處，明確標註「需訪談確認」，不要憑空補。

### 步驟 2：逐模組展開功能 API 與頁面操作
針對模組清單裡的**每一個模組**，用 `${CLAUDE_PLUGIN_ROOT}/skills/rfp-requirement-analysis/templates/模組功能API分析.md` 產一個檔。每個功能固定三段：
- **目標**：一句話講這個功能做什麼。
- **API 表**：`Method | Path | 輸入 | 輸出 | 用途`，涵蓋查詢 / CRUD / 簽核 / 批次 / 檔案交換 / 匯出 / 介接。
- **頁面操作表**：`操作(按鈕/動作) | 對應 API | 說明`，把畫面上的每個按鈕對到 API。

每個模組檔開頭要寫「來源章節」「補充參照」與「共通設計約定」（狀態機、個資遮罩、軌跡），讓檔案自帶上下文；結尾固定收一個 `## 設計備註（跨功能）` 區塊，放本模組跨功能的規則與註記。

**覆蓋粒度（避免漏拆，這是 eval 最常見的缺口）**：
- **展開「補充參照章節」的衍生功能**：RFP 主章節常以「詳見 X.X」或散在他章的方式埋功能。模組檔頭的「補充參照」要列出這些章節，並把它們衍生的功能**實際展開成功能列**（例：編號池/流水號管理、對外 API、報表匯出、附件管理），不能因為它寫在別章就略過。
- **子聚合根各自成獨立功能**：一個聚合根下的每個子聚合根（子資源、子表、子流程）通常各自是一個獨立功能，而非併在父功能裡帶過。把握這個下限：**一個有實質內容的業務模組通常展開出 8～12 個功能**；若只盤出 3～5 個，多半是覆蓋偏粗，回頭檢查是否漏拆子聚合根與補充參照。
- **橫切樣板只在 RFP 明文要求才落地**：個資遮罩 / unmask、簽核、稽核這類橫切，**只有當該模組的 RFP 文字確實要求時**才寫進該模組（並引用索引的共用服務）。不要因為「其他模組有」就預設替每個模組都套上遮罩/解遮罩功能——預設套用會製造黃金版沒有的虛功能。

### 步驟 3：抽出跨模組共用 API 與命名慣例（關鍵）
全系統共用的橫切服務**只設計一份**，各模組僅「引用」不得各自重做。在 `00-索引與彙總.md`（用 `${CLAUDE_PLUGIN_ROOT}/skills/rfp-requirement-analysis/templates/00-索引與彙總.md` 骨架）中集中定義：
- **跨模組共用 API**：線上簽核引擎、稽核軌跡、檔案上傳附件、報表/Excel 匯出+批次、個資遮罩/解遮罩、系統介接。每組給 API 表並列出「引用者」。
- **API 命名與設計慣例**：RESTful 複數名詞、巢狀路徑表聚合、動作子路徑動詞、統一回應封套、分頁、個資遮罩、簽核狀態機。命名補例（沿用這套，避免飄移）：
  - 複數名詞用領域實際字（如土地→`land-parcels`、樓層→`floors`、合約→`contracts`），不用泛稱 `items`。
  - **狀態切換用 `PATCH`**（如 `PATCH /api/contracts/{id}/status`），不要每個狀態各開一支 POST 動作端點。
  - **匯入與匯出拆成不同端點**（如 `POST …/import` 與 `GET …/export`），不要併成一支。
- 各模組檔內出現的同義端點（各自的 `/approvals`、`/unmask`、`/export`）要在索引註明它們是對共用服務的「領域別封裝」。

### 步驟 4：覆蓋檢查與收尾（if-then 補漏迴圈，非終點報告）
覆蓋檢查不是「跑一次寫結論」，而是一個**必須複查通過才能收斂**的迴圈：
- **覆蓋缺漏檢查（偵測）**：逐章比對 RFP（業務章節 + 介接章節 + IT 非功能章節），確認每一條業務功能都已落到某模組某功能。
- **補漏迴圈（補救回邊，強制）**：**若覆蓋缺漏檢查發現任一業務功能未對應到某模組某功能，則對受影響模組回頭重跑步驟 2 補展開缺漏的功能列、重新用機械統計（數 `## 功能` 標題數）數該模組功能數、回填索引後再比對一次**；缺漏可能來自三類，逐類對照修補：補充參照章節的衍生功能未展開 → 補展開；子聚合根被併在父功能裡帶過 → 拆成獨立功能；橫切治理要求未落地或落錯位 → 補進共用服務或對應模組。**唯有複查（再比對一次）通過、不再有未對應功能，才可下「無缺漏」結論**；否則持續迴圈，不得以「列出缺漏清單」當終點交差未補的功能。
- **統計**：分析檔數 / 功能數 / API 數，寫進索引的模組清單表合計列（用機械統計，數 `## 功能` 標題數，不要憑感覺估）。每次補漏迴圈後重新統計，確保數字與檔案現況一致。
- 跨模組/IT 平面散落的橫切要求（批次監控台、效能監控、公告停機…），若不屬單一模組，集中列為「待補強 / 獨立治理模組」，避免各模組重複實作。
- 明確下結論：**無缺漏**（已通過複查）或 **列出仍待訪談確認、無法自行補齊的項目**（已補齊者不得列為缺漏）。

## 大量功能時的並行策略

當模組數多、功能數上看上百個時，**逐模組拆分、可並行處理**是本流程成功的關鍵：
- 先在主流程完成步驟 1（需求分析報告）+ 步驟 3 的命名慣例與共用 API 草案，建立全域約定。
- 再用 subagent（Agent 工具，general-purpose 或 fork）**一個模組一個 agent 並行展開**步驟 2，每個 agent 拿到：該模組的 RFP 章節摘錄、`${CLAUDE_PLUGIN_ROOT}/skills/rfp-requirement-analysis/templates/模組功能API分析.md`、以及步驟 3 的共用 API/命名慣例約定，要求它只負責自己那一檔、沿用共用約定、不重畫橫切服務。
- 全部回來後，主流程做步驟 4 的覆蓋檢查（對照模組清單，確認每個模組檔都產出且功能數對得上），再回填索引統計。
- 並行的代價是約定漂移，要前後兩道一起守：
  - **預防（派工前）**：務必在派工前把命名慣例、回應封套、狀態機、共用 API 清單先定稿並一字不差地交給每個 agent。
  - **偵測（回收時，強制）**：subagent 回來不可照單全收。**逐檔比對每個回傳模組的端點命名（複數名詞/PATCH 狀態切換/import 與 export 分離）、回應封套、狀態機是否與步驟 3 定稿約定一致；任一不一致者，退回該模組重生成（把違反的具體約定指明），修正後才納入步驟 4 的收尾統計**。未通過此偵測複查的模組檔，不得計入功能數合計，也不得據以下「無缺漏」結論。

## 品質要求

- 追溯鏈完整：RFP 章節 → 模組 → 功能 → API；每個功能可往上對回章節。
- 共用服務不重複設計；各模組以領域封裝引用。
- 非功能需求落到具體規則與數字，不空泛。
- 不確定處標「需訪談確認」，不臆造。
- 繁體中文輸出。
