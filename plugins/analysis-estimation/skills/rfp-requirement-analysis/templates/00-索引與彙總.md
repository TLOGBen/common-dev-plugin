## 三、API 命名與設計慣例

### 3.1 RESTful 命名
- 資源一律複數名詞;一對多以巢狀路徑表達;動作型操作以子路徑動詞(`…/submit`、`…/approve`、`…/reject`、`…/withdraw`、`…/release`、`…/close`)。
- 即時檢核以 `check-*` / `validate`;取號以 `next-no` / `next-code` / `available`。
- 介接批次統一「`POST …/sync`(或 `/run`)回 jobId → `GET …/{jobId}` 查狀態」非同步模式。

### 3.2 統一回應封套
```jsonc
{ "success": true, "data": {}, "error": null, "meta": { "total": 0, "page": 1, "size": 20 } }
```

### 3.3 分頁
- 列表統一帶 `page`、`size`,回應 `meta` 含 `total/page/size`。大資料量匯出採非同步快照。

### 3.4 個資遮罩
- 含個資之查詢/報表/匯出一律後端依角色強制遮罩(預設遮罩);解遮罩為獨立授權端點,須帶事由並寫 access trail。

### 3.5 簽核狀態機(全系統一致)
- 核心流:`DRAFT → PENDING_REVIEW → PENDING_APPROVAL → EFFECTIVE/POSTED`;退件→DRAFT、撤銷→WITHDRAWN、作廢→VOID。
- 共同規則:核決權限由設定驅動不可 Hard-coded;簽准/退件以 E-Mail 通知;每次異動保留前後值供 diff。
