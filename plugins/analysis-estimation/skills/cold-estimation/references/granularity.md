# 顆粒度規範（盤點品質的關鍵）

> 這份規範必須**一字不差下放給每一個盤點 / 批判 subagent**。盤點品質好壞，八成取決於每個 agent 是否守住同一套顆粒度。原始腳本把它當成 `TAXONOMY + GRANULARITY` 常數注入每個 agent，本檔即其通用化版本。

## 一、包（必須擇一，不可自創）

「包」= 一個可獨立交付 / 部署 / 計價的軟體單位。**包別由專案實際架構決定**，開工時先定一份清單，全程擇一引用。

### 通用預設包（無特殊架構時用這套）

| 包 | 內容 | 對應功能類型常見值 |
|---|---|---|
| 前端 App / 行動端 | 終端使用者的原生/行動畫面 | 畫面 |
| 對外服務前台 | 對外（旅客/客戶/民眾）的 Web 畫面 | 畫面 |
| 前台後端 / BFF | 前台畫面的後端聚合層（不含核心商業邏輯） | API |
| 後台前端 | 內部維運/管理的 Web 畫面 | 畫面 |
| 後台後端 | 後台畫面的後端 API | API |
| 核心服務 API | 跨前後台共用的核心商業邏輯 API | API、界接 |
| 批次 | 排程 / SFTP / ETL / 對帳批次 | 批次 |
| 基礎設施 / 非功能 | HA / 快取 / 備援 / 資安 / 監控 / 壓測 / 環境建置 | 非功能、系統建置 |

> 若專案架構不同（如單體、微服務、純後端 API、資料平台），**替換這份包清單**為符合該專案的分層，但保持「一個包 = 一個可獨立計價單位、畫面與其後端邏輯分屬不同包」的精神。

## 二、功能類型（必須擇一，跨專案穩定）

`畫面 | API | 界接 | 批次 | 非功能 | 系統建置`

- **畫面**：一個使用者可感知的操作頁面/畫面。
- **API**：畫面背後或服務間的內部商業邏輯端點。
- **界接**：對外部系統的整合端點。
- **批次**：排程 / 檔案交換 / 對帳 / ETL。
- **非功能**：HA / 快取 / 備援 / 資安 / Log / 壓測等品質屬性工項。
- **系統建置**：版本發佈 / 打包 / release / 環境與維運上版等建置工項。

## 三、顆粒度規範（嚴格遵守）

1. **一個「功能列」** = 一個使用者可感知的操作畫面，**或**一支可獨立部署/呼叫的 API/批次/界接端點。
2. **太粗要拆**：例「帳號管理」必須拆成 登入 / 註冊 / 改資料 / 忘記密碼 / 裝置綁定解綁 / 停復用 等獨立列。「報表」要按每張報表拆。
3. **太細要併**：同一畫面內的欄位驗證、單一按鈕，不獨立成列。
4. **畫面與其後端 API 分屬不同包**（畫面 → 前端包；其後端邏輯 → 服務/後端包），同一邏輯**勿在同包內重複**；跨包的畫面+API 各計一次（不是重複，是不同工項）。
5. **界接**：以「**每一個對外端點**」獨立列（同一外部系統的查詢/上傳/退件各算一支）。代理閘道 / proxy 只列 1 列整合介面，不展開其後下游。
6. **來源欄** = 對應 SOW / RFP 章節編號（你的 chunk 開頭有章節與行號；條列 1) 2) 屬同節）。
7. **非功能 / 系統建置**：在 `days` 欄給明列粗估天數；其餘類型 `days` 留空（由費率階段依類型計算）。

## 四、回傳結構（每列固定欄位）

```
包：擇一（見上）
模組：該功能所屬的業務模組名
功能介紹：這個功能列的名稱
功能類型：畫面 | API | 界接 | 批次 | 非功能 | 系統建置（擇一）
簡述：一句話說明
來源：SOW/RFP 章節編號
需壓測：true / false（高併發/效能敏感的端點為 true）
days：數字或留空（僅非功能/系統建置由 agent 給；其餘留空）
```
