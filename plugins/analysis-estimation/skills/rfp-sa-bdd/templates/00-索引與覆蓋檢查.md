## 三、BDD 撰寫慣例說明

### 3.1 檔案結構
每個 BDD 檔以 `# M<n> <模組名> — BDD 驗收規格` 開頭,其下每個功能為 `## 功能 N:<名稱>` 區塊,固定三段 `### Goal` / `### Requirements` / `### Scenario`。

### 3.2 Gherkin 繁中關鍵字
| 繁中 | 英文 | 用途 |
|---|---|---|
| `假設` | Given | 前置條件 |
| `而且` | And | 連接前置/結果 |
| `當` | When | 觸發動作 |
| `那麼` | Then | 預期結果 / 驗收斷言 |

### 3.3 REQ 編號規則
- 三段式 `<前綴>-<功能序號>-<需求序號>`,皆補零兩位。
- 每條 REQ 必須可驗收(具體系統行為或斷言),對應至少一個 Scenario 斷言。
- 編號一經發布即固定;新增往後遞增,不回收舊號。

### 3.4 正常 + 異常情境最低要求
- 每個功能至少 1 正常流 + 1 異常/邊界情境。
- 涉及簽核/批次/檔案交換/狀態機者,加寫狀態轉換 / 時序情境。
- 涉及個資者,必寫「預設遮罩」與「解遮罩需授權 + 寫存取軌跡」兩類斷言。

### 3.5 全系統共通驗收主軸(貫穿各模組)
- **二階簽核**:初核+核准、核決權限不可 Hard-coded、退件 E-Mail 通知曾簽核者、簽准通知呈核人、核准前可撤銷、生效後不可撤銷。
- **稽核軌跡**:寫入型操作記前後值+操作人+時間+來源 IP,保留 ≥5 年、唯讀不可竄改。
- **個資遮罩**:自然人敏感欄位預設遮罩,解遮罩走獨立授權端點並留 access 軌跡。
- **帳務時序閘**:已月結禁改、押金未沖銷不可付租、IFRS16 簽准鎖月等。

## 五、給後續執行 / 實作流程的接續提示（任一 TDD 執行流程）

1. **REQ 作為 requirement.md 追溯依據**:每條 `<前綴>-NN-NN` 可直接作為 `/analyze` 產出之 `requirement.md` 條目來源,設計與測試反向引用 REQ,形成「功能 → REQ → 設計 → 測試 → 任務」可追溯鏈。Scenario 可直接轉驗收測試(BDD/e2e)骨架。
2. **共用服務優先**:簽核引擎、稽核軌跡、附件、報表/批次、個資遮罩、介接為橫切共用服務,執行階段實作一份,各業務模組以領域封裝引用,不得各自重實作。
3. **建議執行切分順序**:<共用件先行:系統管理(角色/簽核/稽核/遮罩)→ 基礎資料 → 各業務模組 → 分析 → 轉入 → 橫切監控>。
4. **跨模組強耦合檢核點(保留為整合測試)**:<編號池原子性、雙向同步、月結鎖定、押金未沖銷不可付租、簽准鎖月、銷帳一對多/多對一 等>。
5. **非功能 / 部署面**:<標註「需訪談確認」項目,執行前先澄清避免返工>。
