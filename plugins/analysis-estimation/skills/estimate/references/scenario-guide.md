# 候選方案決策指南

當證據足以形成替代路線，需要產生、淘汰、比較或向 PM 推薦方案時讀取。

## Gate 2：先確認成果大方向

Gate 1 確認案件資料與初始目標後，下一個 PM 決定就是 Gate 2。技術路線探索開始前，先讓 PM 看見本次升級可能追求的成果層級。大方向描述客戶要買到的終點，不預先承諾某個實作：

- 最低必要相容。
- PM 指定的技術線與版本終點。
- 組織可接受的當前穩定版現代化。
- PM 自行描述的其他成果。

用同一張目標矩陣列出重要技術線的現況、可選終點、Agent 推薦、影響與確認狀態。框架保留原版也是一個終點；只有明確需求或 PM 決策能把它標成已確認。若使用者只指定 JDK 17，Spring Boot、Hibernate、Jakarta、建置工具及部署環境仍各自保留原有狀態。

每個方向都說明客戶成果、預期成本特性、主要風險、優點、需要承擔的代價與會保留的契約。`currentDecision.choiceDetails` 可依選項保存這些 PM 可讀內容；PM 選定大方向後，Agent 才依此探索可行性與候選方案。

一項選擇會改變成果、範圍、人天、責任、相容契約、維護生命週期、部署或驗收時，就在聊天中交由 PM 決定。Agent 查明技術事實並提出推薦，使 PM 能從結果與代價作答。

## Gate 4：方案代表不同交付結果

一個方案必須讓客戶買到不同的成果路徑、責任配置、保障或維護模式。純技術內部變體若不改變客戶決定，留在技術設計，不占用 PM 的候選位置。

最多保留三個可行候選。每案以同一組成果與責任口徑比較：

- 會改動哪些能力，哪些保持不動。
- 成功鏈與主要前置。
- 客戶可理解的成本特性。
- 交付與長期維護風險。
- 主要優點與必須承擔的代價。
- 仍可能改變結論的未知。
- 代表性驗收方式。

推薦方案仍保持「推薦」狀態。聊天中的明確 PM 決定才會把對應方案寫入 `selectedScenarioId`。若證據顯示確認過的大方向只有一條可行路線，Agent 說明淘汰理由並請 PM 確認這個單一路線；它不會被 Agent 靜默視為已選定。

## 淘汰與推薦

只有在方案違反硬目標、官方／runtime 證明不相容、必要能力不存在且無替代，或破壞必須保留契約時淘汰。證據衝突時保留條件分支，優先取得能分辨路線的證據。

推薦採損失最小化：先滿足硬目標，再比較未知、契約破壞、可驗證性、責任、成本、時程與維護生命週期。推薦理由直接說明 PM 會得到什麼與需要承擔什麼，不固定偏向最便宜、最新或改動最少。

## PM 呈現

方案差異涉及三個以上節點、責任交界或先後依賴時，在聊天使用簡單 ASCII 圖。每張圖只回答一個問題，節點名稱使用 PM 能轉述的業務角色，圖下補上成本、風險、優點與承擔。

方案第一次出現時，同步解釋任何可能歧義的名稱。每個這類方案至少用一個句子交代「開發怎麼走」與「正式交付長什麼樣」，再用一句話對照最相近方案。若方案價值來自分段、切換或過渡策略，補一張小圖；不要只在 PM 追問後才說明。

例如「分段直達」不能只放在比較表標題。第一次呈現時就說明：開發與驗證依可獨立檢查的步驟前進，過渡機制只協助定位問題，正式環境最後一次切到單一目標版本；它和「一次跨代」的差異，是前者逐段隔離風險、後者把跨層問題集中到最後整合。這個說明描述方法，不代表固定推薦哪一案。

正式要求選案前，各候選使用相同範圍與費率口徑形成可比較暫估。尚未完成時顯示「待同口徑估算」，不以未查證的高／中／低暗示價格。

聊天在 Gate 2 呈現成果大方向，在 Gate 4 呈現由 Wayfinder 收斂出的具體候選方案。每次只要求一個決定；其他重要決定留在待確認清單中，依其對當前方案與人天的影響排序接續詢問。
