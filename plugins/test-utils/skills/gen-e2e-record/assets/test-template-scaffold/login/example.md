## 這個站台怎麼登入（範例情境：一般帳密表單）

最常見的一種登入：一個帳號欄、一個密碼欄、一顆送出鈕，送出後拿到 session / token，之後才能進入受保護頁面。

### 穩定機制（不太會變的部分）

- 登入頁網址、帳號欄、密碼欄、送出鈕的穩定定位法寫在這裡。
  優先用語意定位（label、role、name），少用會隨建置變動的動態 class。
- 登入成功的判斷依據（例如導向某頁、出現某個只有登入後才有的元素），
  不要只靠「等幾秒」就當作登入完成。
- 登入後憑證存哪（cookie / localStorage 的哪個 key），
  若測試需要直接帶憑證跳過 UI 登入，記在這裡。

### 帳號是資料依賴（最容易被忽略的陷阱）

換一個「什麼都能進」的萬用 / 管理員帳號，往往看起來能登入、頁面也開得起來，
但那個帳號名下**沒有你要測的那筆資料**（待辦、訂單、申請單…），
於是測試一路綠燈，卻測到一個空的、跟需求無關的流程。

所以：

- 記下這個流程**該用哪一種帳號**，以及為什麼（它名下有哪些測試需要的資料）。
- 若帳號與被測資料綁定，註明資料的前置條件（誰建的、什麼狀態），
  不要假設隨便一個帳號登進去就能重現。

### 環境眉角（如果有）

- 帳密來源（環境變數 / 設定檔），**不要把真實帳密寫進 template**。
- 多重驗證、驗證碼、SSO 轉址等會打斷自動化的環節，記下對應手法。

## 寫法提醒

- 只放「這個站台的事實」。通用手法（先看畫面、別把錄製當畫面現實）留在 skill，不要複製進來。
- 片段要能直接被測試引用或照抄，越具體越好。
- 驗證過、覺得會再用到，才沉澱；重複比壞抽象便宜。
