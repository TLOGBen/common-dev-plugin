# 成功鏈到人天估算

當 PM 已選方案且成功鏈收斂，需要建立工作樣態、單位費率與內外估算時讀取。

## 先建立工作樣態

從每個 `priced` 成功鏈節點回答：實際要做什麼、可否共享、可否批次、哪些單位需要獨立理解、有哪些例外、完成證據是什麼。形成互斥類型：

- `shared`：只建立一次的共用底座。
- `mechanical`：相同語意、可由工具批次完成的轉換組。
- `quantity`：每個單位仍需獨立理解、修改或驗證。
- `exception`：已由證據辨識的特殊變體。
- `verification`：代表性遷移驗證與成品檢查。

類型是由成功鏈長出來的描述，不是每案都必須湊齊的模板。

## 先決定「團隊如何承作」，再決定乘數

技術盤點會同時得到許多正確數量，例如 48 支 Action、477 條 route、數百個前端呼叫、數十支 DAO。估價前先找出團隊實際能分工、追蹤與驗收的主承作單位：

1. 一位工程師接到這個單位後，是否需要獨立理解其現況與契約？
2. 是否需要形成該單位自己的修改、局部除錯與完成證據？
3. 相同規則能否由共用底座、腳本、產碼或批次轉換處理？
4. 特殊變體能否只估相對一般樣板的差額？
5. 測試人天承接的是哪些對外保障，而非單純重複開發數量？

符合前兩項且無法由後兩項共享的，才適合作為 `pricingUnits`。其餘數量進入 `scaleEvidence`、批次清冊或驗證覆蓋，不再形成第二套全量乘數。

### 三層報價公式

一個常見且容易向 PM 解釋的公式是：

`總人天 = 一次性底座 + Σ(一般功能族 × 一般單價) + Σ(特殊功能族 × 特殊單價) + 批次核對 + 整合／交接`

- 一般單價包含每個功能族都要重做的理解、修改、局部除錯與代表性測試。
- 特殊單價以一般單價為底，再增加該例外真正多出的施工與驗證。
- 批次核對保存全量守恆，例如確認每條舊 URL 都有新承接者；它不把 URL 數改成新建 API 數。
- 整合／交接承接跨功能收斂、成品檢查與對外保障，不以未說明百分比散灌到各列。

例如 48 支 Action 可守恆為「一般正式 Action＋特殊 Action＋共用基底＋未啟用程式」。共用基底只進一次性底座；一般與特殊 Action 依團隊代表切片逐支計價；未啟用程式只做相容處置；477 條 route 另以整批清冊核對。公式因此能同時保存 48 與 477 的證據，又不重複收費。

## 先完成實作與計價方法卡

每個計價工作先回答下列問題；答案要讓沒有參與盤點的工程師能知道從哪裡下手，也讓 PM 能轉述給客戶：

| 欄位 | 要回答的事 |
|---|---|
| `currentConstraint` | 現在由什麼機制承載，目標改變後哪裡會失效或不再符合要求？ |
| `changeMethod` | 實際修改方式、主要落點與承接機制是什麼？ |
| `customerOutcome` | 客戶完成後得到什麼可使用、可維護或可驗收的成果？ |
| `scaleEvidence` | 影響總數、需處理數、例外與代表案例來自哪裡？ |
| `countingRationale` | 為何計一次、計一批，或必須逐件計價？ |
| `rateBasis` | 低／基準／高費率由哪個實際切片、歷史資料或可解釋步驟得到？ |
| `baselineRationale` | 基準單價包含哪些理解、修改、除錯與驗證，為何目前乘數最可能？ |
| `dedupeBoundary` | 本列包含哪些共用操作，與相鄰工作如何互斥？ |
| `pmChangeSummary` | 用 80～160 字說清楚實際改法、數量驅動與完成結果。 |
| `changeTargets` | 逐項列出影響頁面、API 與 repository-relative 檔案；不涉及時明說。 |
| `detailCatalogIds` | 綁定 Discovery 已建立的 canonical 工作集合；不得另建估價用平行清單。 |

方法卡證明的是施工方式，不是增加文件工作。若多列使用同一改法、同一完成證據且沒有獨立目的，先合併成共用或批次工作，再把真正例外獨立列出。

`detailCatalogs.pricingRole` 明確區分該集合是 `pricing-unit` 或 `scope-evidence`。direct-touch 不代表一定逐項乘價：若 87 個檔案依同一批次規則處理，它仍可完整列出 87 項並標為 scope evidence；若 13 類通道各需獨立端點、資料與完成證據，才標為 pricing unit 並讓 `pricingUnits` 對應 13。

## 單位費率

向 PM 解釋最小切片時使用一個真實代表案例，白話列出包含、排除、完成證據與主要變異。PM 核准低／基準／高的同範圍費率；三者代表：

- 低：已知條件順利、例外較少，但工作範圍相同。
- 基準：依目前證據最可能的處理量與收斂成本。
- 高：同一範圍內合理可預見的較多例外、整合與返工上限。

三者不插入不同工作，也不以未說明百分比加成。

## 算法

- `shared`：數量固定為 1。
- 每列公式統一為：`pricingUnits × 單位人天`。`pricingUnits` 是方法卡證明後的施工單位，不由 `kind` 或搜尋命中自動猜測。
- `quantity`／`exception`／`verification` 只有在每個單位都需獨立理解、修改或驗證時，`pricingUnits` 才等於 `needsChange`；同一改法可整批處理時仍可為 1。
- `mechanical` 通常以一組批次工作計價；occurrence count 只作規模證據，真正例外另列。
- 單位人天與列合計都向上取至 0.5 日。
- 對外 CSV 的 `人天` 取內部高值。

`total`／`needsChange` 用來保存影響範圍與數量守恆；`pricingUnits` 才是公式中的真正乘數：

- `shared` 與 `mechanical` 的人天只乘 1。92 支 DAO 可形成「92 支受影響、整批處理 1 次」；只有證明 92 支都要獨立理解與修改，才改為 `quantity`。
- `quantity` 的每一單位都要有相同最小切片；用至少一個一般代表案例說明步驟與耗時。
- `exception` 只承接已辨識的變體，數量來自證據，不用比例猜測。
- `verification` 的數量是獨立可執行的驗證單位，不等於所有搜尋命中數。

全域替換、產碼重生、規則一致的 import／namespace 改寫、route 表產生等工作，通常屬 `mechanical`：估批次腳本、檢查、例外與收斂，而不是按 occurrence 逐筆乘人工單價。

## 用代表切片校準費率

費率不是從檔案大小或框架印象直接指定。選一個能代表該樣態的真實切片，拆出理解、修改、局部驗證與收斂；再說明低／基準／高差異來自哪些已知變異。當不同群組的步驟明顯不同，拆成不同工作樣態；相同步驟只因搜尋命中變多，維持同一批次工作。

## 歷史合理性校準

若有原系統總建置報價、相似案實績或已完成樣本，記入 `calibration`。它是判斷量級的對照，不是硬上限：

1. 先比較兩者成果與責任是否同範圍。
2. 列出本次可沿用的既有需求、流程、資料模型、頁面與業務規則。
3. 標出本次真正新增或重建的能力。
4. 若純升版高值接近或超過原建置成本，逐包解釋客戶為何實質買到重建型成果；說明不足時回到方法卡重審。

### 團隊慣用費率的使用方式

團隊既有的「每支 Action 幾天」、「每個頁面流程幾天」或「一組框架底座幾天」可以作為代表費率，但先完成三項校準：

1. 寫出單位費率內含的開發與測試步驟，讓不同估算者使用相同口徑。
2. 用原始碼證據把一般、特殊、共用與不處理數量守恆，讓單價只乘在適用單位上。
3. 與相似案及原系統建置成本比較量級；差距來自成果或保障差異時保留，來自中繼版本重做、重複數量或未說明緩衝時回到公式重算。

歷史數字是校準訊號，不是倒填目標。可信結果應同時能由下往上重算，也能由上往下說明為何占原建置成本的合理比例。

## 對外成果包

工程工作列服務估算與施工；對外主表服務 PM 說明。把每個計價工作唯一歸入一個 `clientPackage`，通常形成 5～9 個客戶成果包：

- 包名以客戶取得的能力命名，而非框架代號或內部編號。
- `externalSummary` 用單段精簡文字承接對外主表的「功能說明」：先指出客戶可辨識的調整範圍，再保留 2～4 個主要施工動作與一個白話費用驅動，最後交代完成或驗證結果。它不複製內部方法卡，但也不能只寫「調整共用機制」「維持功能正常」等無法支持費用說明的句子。
- `whyRequired` 說明不做會卡在哪裡。
- `deliveryApproach` 用白話說明我們如何處理。
- `customerOutcome` 描述可驗收結果。
- `scopeEvidence` 用數量與代表案例證明規模，同時說明它是否為計價乘數。
- 每個 work item 先用 `effortSplit` 拆出開發／測試的低、基準、高；包人天只由所屬 work item 的高值加總，主表不另填人天。

### 估算模型反證與主動發現

Gate 5 前不要只問「目前公式能不能算」，另以 `estimationReview` 主動檢查目前施工樣態與乘數是否被需求表面文字誤導：需求列出的功能數是否小於共用元件實際擴散面、共用一次是否其實要逐頁施工、逐檔估算是否可批次降低，以及升版依賴是否迫使方案改採維護分支或替代元件。

只有會改變範圍、方案、責任、人天或驗收的落差才進 `criticalFindings`。例如「需求初看 4 個功能，證據確認 6 個實際修改面」或「目標框架下查詢元件不能原路沿用，需改採受維護分支並驗證查詢語意」。每項都保存原先假設、證據結論、重要性、估算影響、處理方式及成果包／證據追溯；數量落差再以 `scopeDelta` 把初判數、確認數及 work item 的逐名清單機械對帳。一般套件資訊留在依賴附錄。

### Gate 5 的成果包白話說明卡

在詢問 PM 是否確認總人天之前，依 `clientPackages` 的順序逐包呈現一張短卡。每張約 100 字，通常 80～160 字即可；這個範圍只用來控制閱讀密度，是否完整回答下列四題才是完成判準：

1. **PG 要做什麼**：用 2～4 個具體動作說明施工內容，讓新人 PG 知道從哪裡下手。
2. **為何有這個工作量**：指出共用一次、整批處理、逐功能承接、特殊例外或整合驗證，以及支撐判斷的主要數量。
3. **為何這樣拆開發／測試**：開發人天對應理解、修改與除錯；測試人天對應哪些功能、契約、整合或成品保障。兩者各自說明，不用一句「含測試」帶過。
4. **做到什麼算完成**：用 PM／客戶可理解的建置、操作、相容或驗收結果收尾。

```text
### <客戶成果包>｜開發 X／測試 Y
PG 會先……，再……；這個量級主要來自……，其中開發 X 天用於……，測試 Y 天用於……。完成時應能……。
```

範例文案可描述：先確認查詢整合落點，整批調整共同規則，再處理日期、分頁及原生查詢例外；開發承接改寫與除錯，測試承接查詢、資料型別與交易結果核對。實際開發／測試值使用本案所屬 work item 的加總，不套用別案數字。

短卡的人天直接取該成果包所屬 work item 的高值加總。內容從 `deliveryApproach`、`scopeEvidence`、`countingRationale`、`rateBasis`、`effortSplit` 與 `customerOutcome` 整理；若這些資料不足以解釋人天，回到工作方法卡補證據，而不是另寫一套合理化文案。

正式 HTML 的成果包使用點擊展開。展開後每個 work item 顯示 `pmChangeSummary`、頁面／API／檔案完整清單、基準公式、`baselineRationale` 與關聯的主動發現。數量詞必須能由清單重算：寫「六個既有畫面」就列出六個畫面名稱；只有約數或代表案例時不能宣稱已完成最終確認。呈現細節見 [PM 確認報告設計](${CLAUDE_PLUGIN_ROOT}/skills/estimate/references/pm-report-design.md)。

工程工作可有數十列；對外主表固定只顯示序號、系統功能、功能說明、開發人天、測試人天。`whyRequired`、`deliveryApproach`、`customerOutcome`、`scopeEvidence` 與方法卡細節由 PM 摘要、工作方法及證據附表承接。

把內部資料收斂成對外一列時，先從 `deliveryApproach` 選出真正改變系統的主要動作，從 `countingRationale` 提取「共用一次／逐一承接／整批置換／特殊例外／整合驗證」等白話費用驅動，再用 `customerOutcome` 收尾。`whyRequired` 只有在能讓客戶立刻理解費用必要性時才壓入主句；`scopeEvidence` 留在內部，避免把 48 支 Action、477 條 route 等證據數量變成客戶必須自行解碼的技術清單。

## 去重與覆蓋

每個 `priced` map node 必須恰好由一個 work item 承接。若一列同時承接多個節點，說清楚它們為何共享同一實作；若多列聲稱承接同一節點，先要求各列說明獨立目的、操作與完成證據。

外部責任與確定不異動項目保留在報告的 0 人天區，不混入 work item。未知有上限時可用條件式高值；主要範圍或上限無法成立時，標示現在不能形成正式估算。
