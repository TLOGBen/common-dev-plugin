# RFP SA / BDD 驗收規格（第三段）

把第一段的逐功能 API 分析，對**每一個功能**展開成可驗收的 BDD 規格（預設輸出到專案 `sa/`，一模組一檔 + 一份 `00-索引與覆蓋檢查.md`）。每個功能固定三段：

- **Goal** — 一句話描述該功能的業務目的。
- **Requirements** — 條列可驗收需求，每條以三段式 `<前綴>-NN-NN:<敘述>` 編號。
- **Scenario** — 一個以上的繁中 Gherkin 情境（假設 / 而且 / 當 / 那麼），至少含 1 正常流 + 1 異常/邊界。

## 為什麼這樣切

第一段給了「有哪些功能、各自有哪些 API」，但 API 清單不能直接拿去驗收——它沒說「什麼情況下系統該擋、該回什麼、該寫什麼軌跡」。這一段把每個功能轉成**可機械驗收的斷言**：每條 REQ 是一個可測的系統行為，每個 Scenario 是一個可轉成 e2e / BDD 測試骨架的情境。REQ 編號全系統唯一且穩定，正好作為下游 TDD 執行流程（如 `/baransu:execute`）`requirement.md` 的追溯來源，形成「功能 → REQ → 設計 → 測試 → 任務」可追溯鏈。

## 撰寫慣例（務必嚴格遵守，這是格式一致的關鍵）

### 檔案結構
每個 BDD 檔以 `# M<n> <模組名> — BDD 驗收規格` 開頭，開頭 blockquote 寫「來源 + REQ 前綴 + 共通約定（狀態機 / 個資遮罩 / 軌跡）」。其下每個功能為一個 `## 功能 N:<名稱>(<RFP 子章節>)` 區塊，固定三段 `### Goal` / `### Requirements` / `### Scenario`。

### REQ 三段式編號
- 格式 `<模組前綴>-<功能序號 NN>-<需求序號 NN>`，功能序號與需求序號皆補零兩位，全系統唯一。
- 每條 REQ 必須「可驗收」（描述具體系統行為或斷言，非空泛目標），以便對應到至少一個 Scenario 斷言。寫得出 HTTP 狀態碼、阻擋條件、必填欄位、檢核公式、軌跡內容就寫出來。
- 編號一經發布即固定;新增需求往後遞增，不回收舊號。
- 各模組用不同前綴避免碰撞（例：SYS / BLD / LSE-A~E / TNC-A~E / ANA / MIG / OPS）。出租、承租等大模組以子段（A~E）對應次模組。
- **子段字母對齊第一段索引、不自選**：A/B eval 顯示常見偏差是子段字母選錯（如該用 `TNC-C` 卻寫成 `TNC-A`）。子段字母必須照步驟 2 在索引建立的「REQ 前綴 ↔ 模組」對照表，依次模組在來源的固定順序指派，**不可逐檔即興選字母**——否則跨模組編號會對不上、追溯鏈斷裂。

### 繁中 Gherkin 關鍵字
| 繁中 | 英文 | 用途 |
|---|---|---|
| `假設` | Given | 前置條件 |
| `而且` | And | 連接前置/結果 |
| `當` | When | 觸發動作 |
| `那麼` | Then | 預期結果 / 驗收斷言 |

情境本體放在 ` ```gherkin ` 區塊，以 `**情境 N:<標題>**` 標記。

### 正常 + 異常最低要求
- 每個功能至少 1 個正常流 + 1 個異常/邊界（阻擋、檢核失敗、權限拒絕、時序違反、唯一性衝突、除零等）。
- 涉及簽核 / 批次 / 檔案交換 / 狀態機的功能，額外加寫狀態轉換 / 時序情境（月結鎖定、二階簽核退件、押金未沖銷阻擋、排程冪等重跑）。
- 涉及個資的功能，必寫「預設遮罩」與「解遮罩需授權 + 寫存取軌跡」兩類斷言。

### 載荷與命名沿用來源（不自創）
REQ 與 Scenario 裡提到的資源名、端點、狀態值，**一律沿用第一段功能 API 分析檔的實際命名**（如來源用 `/api/workplaces`、`PATCH …/status`、狀態 `EFFECTIVE` 就照用），不要在 BDD 階段另創同義詞。簽核狀態機與個資遮罩的呈現也跟隨來源檔的用語，維持「需求分析 → BDD」載荷一致，斷言才對得上設計與測試。

### 全系統共通驗收主軸（貫穿各模組，撰寫時隨功能帶入）
- **二階簽核**:初核+核准、核決權限不可 Hard-coded、退件 E-Mail 通知曾簽核者、簽准通知呈核人、核准前可撤銷、生效後不可撤銷。
- **稽核軌跡**:寫入型操作記前後值 + 操作人 + 時間 + 來源 IP，保留 ≥5 年、唯讀不可竄改。
- **個資遮罩**:自然人敏感欄位預設遮罩，解遮罩走獨立授權端點並留 access 軌跡。
- **帳務時序閘**:已月結禁改、押金未沖銷不可付租、IFRS16 簽准鎖月等。

## 工作流程

1. **讀第一段輸出**:讀功能 API 分析索引（模組清單、共用 API、命名慣例）+ 每個模組檔（每功能的目標 / API / 頁面操作）。BDD 的功能數與順序必須與來源逐一對齊。
2. **配 REQ 前綴**:在索引建立「REQ 前綴 ↔ 模組」對照表，確保唯一不碰撞。
3. **逐模組產 BDD 檔**:用 `templates/單模組BDD.md`。對來源檔的每個功能，寫出 Goal + Requirements（把 API 表/頁面操作裡的規則翻成可驗收 REQ）+ Scenario（正常 + 異常，按上述最低要求）。
4. **產 `00-索引與覆蓋檢查.md`**:用 `templates/00-索引與覆蓋檢查.md`。含模組清單表（功能數 / REQ 數 / Scenario 數，機械統計）、REQ 前綴對照、撰寫慣例說明、覆蓋檢查結論、給下游執行流程（如 `/baransu:execute`）的接續提示。

## 大量功能時的並行策略

功能數上看上百個時，**逐模組拆分、可並行**是成功關鍵：
- 主流程先定稿 REQ 前綴對照表 + 撰寫慣例（Gherkin 關鍵字、三段式編號、共通驗收主軸），作為全域約定。
- 再用 subagent **一個模組一個 agent 並行展開**，每個 agent 拿到:對應的來源模組檔、`templates/單模組BDD.md`、它的 REQ 前綴、撰寫慣例與共通驗收主軸。要求它只產自己那一檔、嚴守三段式格式與繁中 Gherkin、每功能達到正常+異常最低要求。
- 全部回來後，主流程做覆蓋檢查與統計回填。
- 派工前務必把 REQ 前綴、Gherkin 關鍵字表、共通驗收主軸一字不差交給每個 agent，避免編號碰撞與格式漂移。

## 覆蓋檢查與收尾

- 逐模組比對來源功能 API 分析檔的 `## 功能` 標題數 vs BDD 檔的 `## 功能` 標題數，必須**逐一相符**（例：161 = 161）。把對照表寫進索引。**若 BDD `## 功能` 數 ≠ 來源功能數**：依對照表定位是哪幾個來源功能在 BDD 缺漏 → 對每個缺漏功能補寫該功能的 `### Goal` / `### Requirements` / `### Scenario` 三段（達 ≥1 正常 + ≥1 異常最低要求、沿用來源命名）→ 重跑下一條的機械統計後再下結論，**不得僅列缺漏清單即收尾**。
- 機械統計各檔功能數 / 唯一 REQ 編號數 / 情境區塊數，回填索引合計列（用掃描，不憑感覺）。
- 確認每個 REQ 前綴都實際出現於 BDD 檔；確認每功能皆含 Goal/Requirements/Scenario 三段且 ≥1 正常 + ≥1 異常。**若並行回收的某模組檔缺 ≥1 異常情境，或其子段字母與步驟 2 的「REQ 前綴 ↔ 模組」對照表不符**：把該模組檔退回原模組 subagent，連同對照表中它應使用的子段字母與缺項清單一起重派，要求重產該檔；**主流程不在回收檔上手改**，待重產檔回來後再併入統計與覆蓋檢查。
- 明確下結論:**無缺漏** 或列出缺漏清單;非功能例外（如採 SSO 故原生密碼政策無對應情境）要標為「已知合理例外」。

## 給下游執行流程的銜接（如 /baransu:execute）

在索引結尾寫接續提示:每條 `<前綴>-NN-NN` 可直接作為 `requirement.md` 條目，設計與測試反向引用 REQ 形成追溯鏈;Scenario 可直接轉驗收測試骨架;共用服務優先實作一份;建議執行切分順序（共用件先行）;跨模組強耦合檢核點（保留為整合測試）;需訪談確認的非功能/部署面先澄清。

## 品質要求

- 功能數與來源逐一相符，無漏寫。
- REQ 可驗收、三段式編號唯一穩定;每功能 ≥1 正常 + ≥1 異常情境。
- 繁中 Gherkin 關鍵字（假設/而且/當/那麼）一致使用。
- 個資、簽核、帳務時序的共通主軸隨功能帶入斷言。
- 繁體中文輸出。

## 模板

- `templates/單模組BDD.md` — 單模組 BDD 骨架（含單功能 Goal/Requirements/Scenario 區塊範本，可重複貼用）。
- `templates/00-索引與覆蓋檢查.md` — 索引、REQ 前綴對照、撰寫慣例、覆蓋檢查、execute 接續提示骨架。
