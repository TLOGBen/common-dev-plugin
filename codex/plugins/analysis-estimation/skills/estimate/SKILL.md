# Estimate｜既有系統評估

協助 PM 把陌生既有系統整理成一份能向客戶 IT 說明、能回到技術證據、也能解釋人天來源的評估。Agent 承擔技術複雜度；PM 專注於目標、範圍、責任、保障與費率等需要人類承諾的決定。

```text
聊天確認案件 → Gate 2 選成果大方向 → $wayfinder 盤點成功路線
            → Gate 4 選方案 → 形成工作與人天 → Gate 5 確認 → 產出 CSV／報告
```

## 核心思維

把評估視為一場「從客戶成果走回必要工作」的推理：

1. **先看客戶要買到什麼**：把成果、保留行為、驗收方式與責任邊界說成可確認的句子。
2. **再畫成果如何成立**：用成功鏈連接能力、前置、外部責任、相依關係與完成證據。
3. **把未知變成有作用的迷霧**：一項未知值得追蹤，是因為它仍可能改變可行性、方案、責任、範圍或人天。
4. **選最能推進決定的證據**：優先查證能排除方案、改變責任或縮小人天區間的事實。其餘資訊保留為背景即可。
5. **讓正確的人做決定**：Agent 查明程式、依賴、執行與資料事實；PM 決定客戶願意購買的結果與保障。
6. **在證據足以承諾時收斂**：剩餘未知能描述影響、合理上限與責任時，方案即可進入估算。
7. **從成功鏈形成工作**：每項工作承接一個必要成功條件，並具有數量、完成證據、責任與單位人天。
8. **維持雙向追溯**：人天能回到成功條件；成功條件也能找到唯一工作、外部責任或明確未知。
9. **先證明改法，再決定乘數**：搜尋命中、頁面、路由、DAO 與 SQL 數量先用來說明影響範圍。每項工作另以明確的 `pricingUnits` 保存真正計價乘數；只有每個單位確實需要獨立理解、修改或驗證，才讓它等於需處理數。
10. **用客戶成果組織對外說明**：工程工作可以細，PM 主表維持少量可購買、可驗收的成果包。對外每一列都保留一條完整但精簡的說服鏈：這次處理哪個範圍、主要進行哪些同層級動作、完成後如何確認。每個成果包都能下鑽到互斥工作與技術證據。
11. **把選定方向當成待驗證假說**：PM 決定想買到的成果；Agent 主動尋找足以推翻、改寫或轉移維護責任的依賴證據。方案經得起反證後才成為可估算路線。
12. **用團隊真正承作的單位估價**：盤點回答「碰到多少」，估價回答「團隊要獨立承接、修改並驗收幾次」。共用底座算一次；規則一致的工作算一批；可由一位工程師負責到完成的功能族逐件計價；已辨識的特殊變體只加例外差額；測試依對外承諾的驗證責任另行拆分。
13. **讓估算量級經得起現實比較**：這條要解決「公式完整，總價卻比相似案或原系統建置成本更不合理」的問題。先由工作方法自然算出結果，再用相似案、團隊慣用費率與原系統建置成本找出承作單位過細、重複計價、漏列保障或範圍不同。歷史比較與差距計算是 MOP；PM 能說明本案為何較高或較低、客戶多買到或少承擔什麼，才是 MOE。校準用來發現公式問題與解釋差距，不用來把答案倒填成既定數字。
14. **讓每個流程機制都服務 PM 的最終任務**：這條要解決「gate、hash、腳本、地圖與 validator 全部 PASS，PM 仍無法選方案、看懂人天或向客戶說明」的問題。新增或保留任何機制前，先列出它對最終目標造成的正面影響，再逐項標示 MOP 或 MOE。MOP 證明機制可靠運作；MOE 證明 PM 能完成決策、估算或客戶說明。以 MOE 判定完成；MOP 在能降低已辨識風險，或能讓 MOE 穩定重現時保留。
15. **把主動發現放回它影響的評估項目**：Gate 5 前反證需求表面數量、施工樣態與依賴路線。若 CR 的人工初判是 N 項、證據盤點是 M 項，以 `scopeDelta` 保存 N／M 與對應 work item，並由 `changeTargets` 逐名列出 M 個落點；M 與清單筆數不一致時回到 discovery 補查。若升版／混合案的依賴證據改變可行路線，保存原路線、證據支持路線及人天／責任影響。兩者都寫入 `estimationReview.criticalFindings` 並連回成果包與證據，只在所屬成果包的下鑽內容顯示，避免 PM 在沒有項目上下文時解讀孤立警示；任一應有分支未完成就不得進入 Gate 5。
16. **一份盤點，多種投影**：Discovery 只在 `detailCatalogs` 建立一次 canonical 工作集合，分類為逐項處理、重新產製或範圍證據。Wayfinder 只有分類會改變方案、計價或責任時才開票；work item 以 `detailCatalogIds` 綁定同一批 stable IDs；Gate 5 與 generator 只核對或投影，不重掃 repository、不建立平行清單。direct-touch 的宣稱數與完整 items 不一致、集合未引用或 ID 重複時阻擋正式估算。

新證據可能改變先前判斷。Agent 依當前 Frontier 回到最相關的問題重新推理，讓方法適應案件，而非把案件塞進固定分析順序。

### 機制正當性檢查

設計或修改流程時，先為每個機制寫出「要解決的失敗、對最終目標的正面影響、MOP／MOE 分類與保留理由」，再用同一組問題檢查：

1. **最終目標**：這次要讓 PM、客戶或工程團隊真正完成什麼？
2. **正面影響**：這個機制會使哪個決定更正確、哪份估算更可信，或哪段說明更容易被理解？
3. **MOP／MOE**：它只證明流程有執行，還是直接證明使用者得到有效結果？
4. **因果與反事實**：拿掉後會出現哪個具體損失？這個損失是否已有證據，或只是為了防範想像中的失敗？
5. **最小充分做法**：能否直接檢查最終產物或使用者結果，取代額外狀態、代理指標與生命週期機制？

直接觀察最終成果的 MOE 優先。例如「fresh reader 能只看對外表向客戶解釋費用」直接驗證說服力；「保存 review PASS、hash 相符、欄位存在」只證明審查機制運作。後者若沒有額外且已證實的風險，不增加為正式完成條件。

## 把 PM 的注意力用在決定上

Gate 是交還承諾權的停等點，也是案件進度的投影。只有當不同答案會改變客戶成果、範圍、方案、人天、責任、契約、部署、生命週期或驗收保障時，才停下來等待 PM；其餘 gate 寫回案件主檔後由 Agent 繼續推進。

每次要求 PM 閱讀或回答前，先準備一張值得花時間的決定：

- **要決定什麼**：用客戶成果或責任語言命名。
- **為什麼由 PM 決定**：指出涉及的承諾、費用、風險或組織責任。
- **哪些資訊值得看**：只呈現足以區分選項的差異；技術證據與數量明細放在可展開層。
- **各選項買到什麼**：分別說明成果、成本特性、主要風險、責任／前置、長期影響與驗收差異。
- **Agent 建議什麼**：提出推薦、理由與成立條件，同時保持案件為未選狀態。
- **哪些可以稍後決定**：讓 PM 只承擔目前真正影響方向的選擇。
- **選完後會發生什麼**：列出 Agent 將自動接續的查證、收斂或產出。
- **其他（自行輸入）**：接受 PM 自己描述的成果方向或組合；先回述理解，再重組分析。

方案名稱若包含團隊自訂、壓縮語意或容易誤會上線方式的詞，例如「分段直達」「相容遷移」「雙軌」「一次跨代」，第一次出現時就先翻成白話：一句話定義、開發過程、正式交付型態，以及和相鄰方案的真正差異。先完成解釋再請 PM 選擇；涉及先後順序時，用 3–7 個節點的 ASCII 小圖說明。PM 不需要靠追問才能知道「分段」是否代表多次上線，或「直達」是否仍會保留中間版本。

當答案可以由程式碼、設定、建置、執行證據或唯讀資料查明時，Agent 直接查明並負責結論。PM 的時間留給需要承諾的選擇。

一項選擇只要會改變客戶買到的成果、納入範圍、人天、責任、相容契約、維護生命週期、部署方式或驗收保障，就屬於 PM 決定。Agent 提供事實、可行選項與推薦；PM 的明確回答使推薦成為案件承諾。保留現行版本、沿用既有部署或排除一項框架，同樣是需要被看見的選擇。

使用者先前已清楚提供答案時，Agent 以白話回述並寫入決策紀錄，使 gate 完成，而非重複詢問。Gate 6 通常呈現交付完成；只有交付格式、目的地或發布責任仍會改變承諾時才形成停等。

建立 `currentDecision`、判斷是否值得停等或設計各 gate 的決策內容時，讀 [references/pm-decision-pauses.md](references/pm-decision-pauses.md)。

### Gate 2 先選大方向

案件資料足以辨識主要技術線後，在 Gate 2 先讓 PM 決定這次要解到哪一層。常見方向包括：

- **最低必要相容**：達成指定目標，保留其餘可延續的技術與契約。
- **指定技術線升級**：明確列出要升級的 runtime、framework、前端工具、資料層或部署型態。
- **當前穩定版現代化**：把主要技術線帶到組織可接受的當前穩定版本，並承擔連鎖遷移。
- **其他成果方向**：由 PM 描述客戶真正要買到的狀態。

每個方向都說明客戶成果、預期成本特性、主要風險與會保留的契約。PM 選定大方向後，Agent 才依此探索可行性與候選方案。Gate 4 再呈現經證據驗證、真正可落地的具體路線。

Gate 1 與 Gate 2 直接在聊天中完成，聚焦案件資料、成果方向及工作分工。大方向成為共同終點後，**直接呼叫 `$wayfinder`**，以它的 Markdown 地圖與決策票展開成功鏈、技術迷霧、責任與候選路線；Gate 4 再把已被證據支持的路線交給 PM 選擇。Wayfinder 負責找路，Estimate 負責把選定路線轉成人天與交付成果。

## 先建立共同案件事實

案件主檔讓 PM 和 Agent 從同一份事實接續工作；聊天是 V3 的主要決策介面：

1. 既有案件以 `scripts/case_state.py validate <case-root>` 驗證 `assessment-state.json`；新案件以 `scripts/case_state.py init <case-root> --name ... --goal ... --mode ...` 建立主檔。
2. `init` 或 `validate` 成功即代表主檔可用。先取得足以說明 Gate 2 選項的最小現況資訊，在聊天中讓 PM 決定成果大方向與工作分工。
3. Gate 2 確認後呼叫 `$wayfinder`。地圖的 destination 使用 PM 選定的成果；每張票只承接一個仍會改變成功路線的決定或查證問題。
4. 技術查證票由 Agent 自動推進；涉及成果、範圍、成本、責任、生命週期或驗收保障的票，才在聊天中用完整決策包停等 PM。
5. 成果、迷霧、證據、方案、成功鏈、工作與 PM 決定寫回同一份案件主檔；Wayfinder 的 `map.md` 與票據保存方案形成過程。兩者用穩定名稱互相連結，不互相複製整份內容。
6. 架構、成功鏈、方案差異與責任邊界以簡短 ASCII 圖投影在聊天與 Markdown，讓 PM 在同一個決策介面完成理解、選擇與追問。

案件結構、revision 與事件寫入契約見 [references/case-state.md](references/case-state.md)。

### 聊天中的決策接續

`currentDecision.requiresHuman: true` 的選項、自由輸入與提交在目前聊天呈現。Agent 擁有票與票之間的推進責任；PM 只回答確實需要其承諾的問題。上一票被接受代表 Agent 取得了繼續工作的輸入，不代表這一輪已完成。

Agent 收到 PM 答案後，以 `record-answer` 寫回同一案件 revision，隨即完成該答案已解鎖的查證、地圖更新與下一步。當下一個問題仍可由 Agent 查明時繼續工作；只有抵達下一個真正的 PM 決定或完整完成時才交還控制權。這避免 PM 與 Agent 在兩張票之間互相等待。

每個決策包先說明「要決定什麼、為什麼由 PM 決定、各選項買到什麼、Agent 建議、選完後 Agent 會做什麼」，再提供 2–3 個互斥選項與「其他」。技術名詞在原地用白話解釋；詳細證據放在其後或連結檔案，不要求 PM 先讀完整技術盤點。

Host 原生授權、工具 approval 與敏感操作確認仍由 Host 介面承接；它們不是 PM 案件決策，不寫成 `currentDecision`。使用者主動在聊天給出的明確答案可直接接受，不要求換到另一個介面重答。

## 探索陌生系統

先把案件模式視為可修正的假說：升版、CR 或混合型。再從客戶成果辨識哪一段成功鏈仍在迷霧中，選擇適合的證據來源。常見證據包括原始碼、建置設定、實際依賴、產碼鏈、部署描述、執行結果、唯讀 DB、內網診斷與客戶責任資料。

盤點的價值來自「這項事實會改變哪個決定」。單純增加檔案數、框架名稱或頁面清單，只有在它們能支撐成功鏈、方案或數量時才進入評估主線。

Gate 2 大方向確認後，陌生系統的事實蒐集可由 3–5 個唯讀 sidekick 並行：Codex 優先使用乾淨上下文的 `gpt-5.6-luna`／`max`，Claude Code 使用 Host 可用的 Haiku／Sonnet research subagent。每個工作包具備互斥證據面、固定目標、權限邊界與可驗收格式；sidekick 回傳清單、數量、代表案例、來源定位、否定結論邊界與迷霧，不選方案、不估人天、不寫案件主檔。

主 Agent 負責切包、抽查承重證據與所有「未找到」結論、解釋矛盾、跨包去重、形成成功鏈與方案，並把 PM 的答案轉成案件承諾。並行化用來加速盤點，不分散整體理解與判斷責任。派工前讀 [references/inventory-sidekick-brief.md](references/inventory-sidekick-brief.md)。

升版與混合案件先建立目標矩陣：每條重要技術線列出現況、可選終點、Agent 推薦、決定者、對成果／人天／責任的影響及確認狀態。使用者指定 JDK 17，只能確認 JDK 的終點；Spring Boot、Jakarta、前端建置工具與部署型態各自保留原有決定狀態。技術相容證據能說明某條路可行，仍由 PM 決定是否把該路納入客戶成果。

### 主動找出會推翻方案的依賴

Gate 2 確認的是客戶想抵達的方向，不是某條技術路線已經成立。升版與混合案件在形成 Gate 4 候選方案前，Agent 主動完成一輪「依賴可持續性反證」：

1. 從實際 resolved／deployed classpath、lockfile、systemPath、私有 JAR、產碼工具與 runtime module 建立 dependency coverage，而非只讀 manifest 的直接依賴。
2. 從跨 major 邊界、codegen／APT、框架整合 adapter、dialect／registry／contributor／SPI、私有修改版／fork／無原始碼元件、生命週期終止與執行語意變化等訊號，找出會改變方案的依賴。
3. 對每項依賴提出反證問題：「什麼事實會讓目標版本不可採用、需要替代路線，或使長期維護責任轉到我方？」再優先尋找官方文件、上游 issue／release、實際使用全集與代表性 runtime probe。
4. 先以整個 package／artifact／設定入口建立使用全集，再分類高風險 API 與語意；單一 factory、class 或搜尋詞只作為線索，不作為完整 footprint 的代理。
5. 分開記錄上游維護者與我方改造責任，並區分「可以編譯／namespace 可用」和「上游支援／執行語意可承諾」。
6. 遇到 unsupported、unknown 或維護責任不明時，形成停留既有線、採 fork、替換元件、自行維護或供應方承接等可落地策略。Agent 先查清技術事實；只有策略會改變客戶成果、成本、責任或生命週期時才交給 PM 決定。

每輪結束時，案件主檔要能回答：實際依賴全集如何取得、哪些元件承重、目標相容性由何證據支持、採用哪條策略、誰承擔後續責任，以及是否仍有事實會推翻方案。細節與資料契約見 [references/dependency-behavior.md](references/dependency-behavior.md)。

- 開始廣泛探索或判斷盤點面向時，讀 [references/discovery-guide.md](references/discovery-guide.md)。
- 判斷證據價值、成功鏈完整度或收斂時機時，讀 [references/evidence-and-success-chain.md](references/evidence-and-success-chain.md)。
- 升版／混合型案件，以及觸及 framework、runtime、產碼、界接或私有元件的 CR，讀 [references/dependency-behavior.md](references/dependency-behavior.md)。此時以 SBOM 找出實際組成，再追查整合足跡、擴充點與語意相容，而非停在版本清單。

## 形成方案與人天

Gate 2 之後的候選方案盤點由 `$wayfinder` 直接承接。它以 PM 選定的大方向為 destination，把會改變成功路線的未知開成研究／決策票，逐步收斂為客戶真的可以採用的不同成功路徑。Estimate 從已關閉的票與 Decisions-so-far 取得方案依據，比較成果、成本、交付風險、長期維護責任及外部條件；差異不足以改變 PM 決定的變體合併說明。

Estimate 使用 Wayfinder 的 canonical Markdown map／tickets，並遵循 Wayfinder 自己的呈現契約；對 PM 的當前摘要以聊天內 ASCII 路線圖與白話決策包呈現。若 `$wayfinder` 在目前環境不可用，清楚標示 `WAYFINDER_UNAVAILABLE`，以相同的 destination／決策票語意建立本地 Markdown 方案地圖，且不宣稱已執行 Wayfinder。

Agent 的推薦保留為推薦，直到 PM 經目前有效的單一輸入介面明確選定。`selectedScenarioId` 只承接具有決策紀錄的方案；原始需求未提到的技術線維持待確認，現況可建置也不會自動把「保留現況」轉成客戶選擇。Gate 4 的方案名稱不能代替實施方式：第一次呈現時同步說明開發節奏、正式交付幾個版本、過渡機制是否保留，以及成本與風險集中在哪裡。

缺少外部環境、帳號或客戶施工資料，可在範圍已確認後轉成成立條件。尚未確認的升版終點、納入範圍、責任與保障留在 PM 決定中，因為不同答案會形成不同估算。

PM 選定方案後，重新由該方案的成功鏈建立工作樣態。一次性共用工作、可批次轉換、一般數量單位、特殊例外及驗證分開估算：

- 語意相同的大量異動，以「批次工作＋實際例外＋整合／驗證」反映成本。
- 每項數量維持 `總數 = 需處理 + 不處理 + 未知`。
- 已確認不異動的項目為 0 人天；未知以條件式邊界、合理上限或待確認項目呈現。
- 單位人天與列合計採 0.5 人天為最小倍數向上取整。
- 內部版保留同一範圍下的低／基準／高，並在每個工作項目中明確拆出開發與測試；對外 CSV 分別加總兩者的高值。
- 發現兩列可能重疊時，先釐清各自目的、操作、代表案例、完成證據與獨立存在的理由，再依證據決定合併或保留。

### 從技術盤點轉成團隊報價

先選擇團隊能實際分工、追蹤與驗收的主計價單位，再用其他數量證明範圍完整：

- **共用底座**：框架啟動、路由分派、共用輸入輸出、安全、Session、日誌、封裝等只建立一次的能力，以一個成果工作包估價。
- **功能承作單位**：以 Action、頁面流程、DAO 樣態、介接通道等能由工程師獨立理解、修改、局部驗證並交付的功能族逐件計價。每個單位明列開發與測試包含什麼。
- **批次規則**：URL 清冊、namespace/import 改寫、產碼重生、規則一致的 API 或 SQL API 置換，以工具化轉換、核對、例外收斂及整批驗證估價。
- **特殊例外**：上下載、登入、直接 response、特殊交易、客製 SPI、外部副作用等已知變體，按實際例外數增加差額；它仍屬原功能集合，不重新計整份一般工作。
- **交付保障**：代表性回歸、整合收斂、成品檢查、切換／回復與交接，依客戶購買的驗證深度形成明確工作包。

路由、搜尋命中、HTML、SQL、DAO、mapping 與套件數量通常是完整性證據。它們只有在每一個單位都需要獨立施工與完成證據時，才成為乘數。例：48 支 Action 可以是功能承作單位；同屬這 48 支的 477 條 route 則是路由守恆清冊，兩者共同說明規模，但不彼此相乘。

團隊既有估價方式或相似案可提供代表費率，例如「一般 Action 每支含路由接入、參數、回應、局部除錯與代表性測試」。Agent 要把這個費率拆成可說明的步驟、確認適用單位與例外，再用它計算；這樣既延續團隊經驗，也保留重新估算與說服客戶的證據。

每個計價工作在套人天前先完成一張「實作與計價方法卡」：

- **現況限制**：目前哪個機制承載功能，目標版本後為何需要處理。
- **實際改法**：會改哪些類型的檔案／設定，採共用承接、批次轉換、逐件調整或例外處理中的哪一種。
- **客戶取得成果**：完成後可使用、維護或驗收的結果。
- **規模證據**：受影響總數、需處理、不處理、未知及代表案例。
- **計價理由**：為何計一次、計一批，或每個單位都需要獨立工作；費率由哪個代表切片或歷史資料校準。
- **計價單位**：與影響總數分開記錄。共用／批次工作通常是 1；只有具獨立施工與完成證據的單位才逐件計價。
- **完成證據**：什麼可重複檢查的結果代表這項工作完成。
- **去重邊界**：本列已包含什麼，哪些工作由其他列或外部責任承接。
- **修改落點**：以 `changeTargets.pages/apis/files` 逐項列出頁面、API 與 repository-relative 檔案；寫「六個畫面」就必須列出六個名稱，不涉及的類別明說原因。
- **工作集合**：以 `detailCatalogIds` 綁定 Discovery 建立的 canonical workset。`direct-touch` 完整逐項列出；`generated` 保存來源、重產與核對；`evidence-only` 明說只作覆蓋證據。每組另標示是計價單位或不作人工乘數的範圍證據。
- **基準人天理由**：以 `baselineRationale` 說明基準單價包含的理解、施工、除錯與驗證，以及為何使用目前乘數；`pmChangeSummary` 用 80～160 字整理修改方式、數量驅動與完成結果。

方法卡的目的是讓另一位工程師能描述實作步驟，也讓 PM 能說明費用來源。只有列出名詞、檔案數或搜尋命中的工作仍是影響盤點，尚未形成可計價工作。

當案件能取得原系統建置報價、相似案實績或已完成樣本時，建立合理性校準：比較成果範圍、已存在且沿用的資產、實質重寫比例與人天。純升版的高值接近或超過原系統總建置成本時，逐項指出客戶額外買到的重建型成果；若主要工作只是沿用既有功能，回到方法卡重新檢查重複計價、驗證數量誤當施工數量及過高單價。

對外說明不直接複製全部工程工作列。把工程工作唯一歸入少量「客戶成果包」，通常 5～9 包即可支撐報價說明。對外主表只顯示「序號／系統功能／功能說明／開發人天／測試人天」；系統功能使用客戶辨識得出的業務區塊或採購成果，明確採購的 JDK、Spring Boot、Vue、WebLogic 等技術終點可以具名，內部 class、package、API 編號與工作代碼留在內部。

功能說明以單段文字壓縮四件事：**調整範圍、2～4 個主要動作、白話費用驅動、完成／驗證結果**。費用驅動說明工作量主要來自共用底座、逐個功能承接、整批套件置換、特殊例外或整合驗證中的哪一類，不要求客戶解讀內部數量表。PM 看完一列，應能回答「這筆費用在改什麼、主要怎麼改、為何有這個量級、做到什麼算完成」。必要性、完整實作方法、技術證據、數量算法、責任與低／基準／高仍留在內部文件或其他分頁；若拿掉這些細節後只剩「調整共用機制」「維持功能正常」等空泛句子，就先補回客戶可辨識的施工內容。成果包的開發／測試人天由工程工作加總，沒有另一套手填數字。

Gate 5 詢問 PM 是否核准總人天以前，先逐一說明每個客戶成果包。每包以約 100 字的說明搭配「開發 X／測試 Y」，回答四件事：PG 實際要做哪些工作、工作量由哪些數量或例外驅動、開發與測試為何需要這個量級、完成時可用什麼結果確認。約 100 字是閱讀密度，通常 80～160 字即可；資訊完整與可轉述優先於精確字數。正式 HTML 第一層固定為「本次摘要 → 評估項目與低／基準／高人天 → 折疊技術附錄」；每包以整列按鈕開啟原生 dialog，逐項查看頁面／API／檔案清單、修改重點、基準公式與理由，以及只屬於該包的主動發現。dialog 固定提供頂部關閉與底部「回到評估項目」，關閉後回到原列與原捲動位置。這一層由既有成果包與工作項目整理而成，不新增工作、不重算人天，也不塞入對外五欄主表。

候選方案的判斷見 [references/scenario-guide.md](references/scenario-guide.md)；成功鏈已收斂且 PM 選定方案後，讀 [references/estimation-guide.md](references/estimation-guide.md)。

## 工作權限與證據邊界

案件預設採 `assessment-only`：Agent 可執行讀取、統計、反編譯及隔離分析，也可在確認客戶狀態保持不變後執行 build、test、啟動、瀏覽器、唯讀 DB 與內網診斷。

會改變產品、資料庫、部署環境、外部系統、Git 歷史或業務狀態的操作，由 Host 原生授權與案件責任邊界確認後執行。工具權限、案件範圍與客戶承諾以 Host 授權、聊天中的明確回答及案件主檔為準。

本 Skill 交付技術評估。正式價格、合約與採購承諾由後續商務流程承接。

## 機械護欄的適用位置

機械化用來保存重複性、決定性與一致性，讓 Agent 把注意力留給技術判斷：

- `case_state.py` 保存 schema、revision、事件冪等與數量守恆。
- `generate_outputs.py` 從同一 revision 產生 CSV、Markdown 與 HTML。
- Wayfinder 的 Markdown map／tickets 保存方案問題、決定與依賴關係。
- ASCII 投影把方案、成功鏈與責任差異壓縮成 PM 可在聊天立即閱讀的圖。
- validator 與測試確認公式、manifest、輸出結構與決策狀態。

案件主檔、地圖、腳本與 validator 主要屬 MOP：它們讓決策、重建與計算可靠；ASCII 決策包與 fresh-reader 驗收直接支援 PM 理解及對客戶說明，屬 MOE。機械護欄保留在能降低已辨識風險或讓 MOE 可重複成立的地方，完成仍以 PM 能選方案、理解人天與說明成果為準。

## PM 評估的六個 gate

六個 gate 投影案件進度與人類承諾點；每個 gate 先判斷目前是「進度狀態」還是「PM 決策停等」。Agent 的探索順序由 Frontier 與證據價值決定：

所有 `currentDecision` 與 Gate 5 說明在呈現前，都必須通過 [「直接陳述，不用文字表演」](references/pm-report-design.md#直接陳述不用文字表演) 的逐句檢查。

1. **提供案件資料**：確認案件對象、初始目標及可使用的資料／權限。
2. **選擇成果大方向與工作分工**：決定客戶要買到哪一層成果，以及環境、UAT、壓測與第三方責任。
3. **核對案件理解**：確認成果、保留行為、範圍、責任與驗收語意；技術清單留在次要層。
4. **選擇採用方案**：比較已由證據支持的成功路徑、成本、風險、前置與生命週期後選案。
5. **確認工作內容與人天**：先看本次摘要，再掃讀每包原項目說明與低／基準／高人天；需要確認時點開該包，查看約 100 字修改重點、頁面／API／檔案清單、基準公式與理由、開發／測試拆分、完成結果及只屬於該包的主動發現；最後核准工作切片、數量算法、驗證深度、包含／排除與對外高值。
6. **取得交付成果**：顯示可下載成果與品質狀態；只有交付方式仍需承諾時才停等。

當某個 gate 沒有需要人類承諾的問題，它只是案件進度狀態。當它需要停等，`currentDecision.requiresHuman` 必須為 true，且聊天中的決策包要完整說明 PM 要做什麼、為何重要、選項差異、Agent 推薦與決定後的接續工作。

Gate 2 確認成果大方向後，Agent 立即進入 Wayfinder 方案地圖；Gate 4 的候選路線與 Gate 5 的工作／人天回到聊天，由 PM 明確選定或核准。聊天回覆一項決定後，Agent 自動接續到下一個真正需要 PM 的停等點。

## 交付成果與完成條件

預設交付格式是：

- `assessment-report.md`：現況、方案、成功鏈、新人教學、責任與未知。
- `assessment-report.html`：適合 PM／客戶 IT 閱讀的同源報告。
- `estimate-internal.csv`：低／基準／高、算法、來源與完成證據。
- `estimate-external.csv`：公司對外報價口徑的五欄主表，只含序號、系統功能、功能說明、開發人天與測試人天。

以 `scripts/generate_outputs.py <case-root> --json` 從案件主檔一次生成。案件明確需要 Excel 時，依 [交付手冊](references/deliverables.md) 由同一 revision 建立「對外估算／PM 摘要／工作方法／內部估算／證據與校準」活頁簿；對外估算維持五欄，其餘說明移到其他分頁，公式總數必須與 CSV 及案件主檔一致。Word 或 PDF 仍按案件需要轉換。

正式完成代表：成果成功鏈已收斂；每個計價節點具有唯一承接；責任與未知清楚；數量與 0.5 日公式通過；案件主檔、Wayfinder 決定與交付檔可互相追溯；對外內容完成去識別；fresh reader 直接閱讀實際交付的五欄主表後，能依每一列說出改造範圍、主要動作、白話費用驅動與完成結果，並能說明客戶買到的成果、主要風險、責任與人天意義。

## 公司 SOP 的回饋出口

使用者回饋先在案件本地形成去識別回饋卡。環境具有 Git／tracker、登入、遠端與權限時，Agent 產生 `common-dev-plugin` Issue 草稿，顯示完整預覽並在使用者確認後建立；其他環境以本地回饋卡完成收集。

中央 Issue 保存抽象任務、可遷移根因、影響、期望行為與合成最小重現。客戶、專案、repo、路徑、內網、原始碼、log 與原始產物留在案件本地。正式改善採一個 Issue 對應一個 branch／PR，經跨案驗證及指定維護者核准後合併 `common-dev-plugin/main`。
