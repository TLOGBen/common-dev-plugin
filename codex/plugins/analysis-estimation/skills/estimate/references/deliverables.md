# CSV／Markdown／HTML／Excel 交付手冊

當案件成功鏈、人天與責任已收斂，需要生成、重建或核對交付成果時讀取。

## 預設成果

執行：

```text
python scripts/generate_outputs.py <case-root> --json
```

產生：

- `assessment-report.md`
- `assessment-report.html`
- `estimate-internal.csv`
- `estimate-external.csv`
- `generation-report.json`

CSV 使用 UTF-8 with BOM，便於 Windows Excel 直接開啟；它仍是標準 CSV，不依賴 Office。Markdown 與靜態 `assessment-report.html` 來自同一 state revision，避免手改造成數量漂移。

`assessment-report.html` 是 Gate 5 的主要確認介面。第一層固定為本次摘要、低／基準／高估算列與折疊技術附錄；每列以原生 dialog 顯示逐工項修改重點、基準公式、理由及 `detailCatalogs` 工作集合。巢狀 `<details>` 只投影 state：不重掃 repository，不另建平行細項清單。

## 對外內容

對外主表模仿公司實際報價明細的閱讀密度，只保留五欄，順序固定：

1. `序號`：從 1 開始的純數字。
2. `系統功能`：客戶辨識得出的業務區塊或成果名稱，不放 class、package、framework 工項名稱。
3. `功能說明`：一段精簡但足以說明費用來源的摘要，保留調整範圍、主要動作與完成結果；內部識別、逐檔數量、相容性斷點與詳細驗證方法留在內部文件。
4. `開發人天`：該成果包內工程工作的對外高值開發人天加總。
5. `測試人天`：同一批工程工作的對外高值測試人天加總。

對外主表不放總數算法、責任、範圍證據、低／基準／高、內部緩衝或工程工作數。這些資訊不是消失，而是放在內部 CSV、評估報告或 Excel 的其他分頁。對外每列仍可由 `clientPackageId` 回溯到唯一 work item 集合；開發與測試人天由 `effortSplit` 加總，不另手填一套報價數字。

### 對外一列的語意契約

每列功能說明要讓 PM 不開內部分頁，也能用一句話回答四個問題：

1. **改造範圍**：哪個客戶可辨識的系統區塊、平台能力或明確採購技術線需要處理？
2. **主要動作**：本案實際會升級、置換、遷移、調整、修復或重建哪些同層級內容？通常保留 2～4 個主要動作。
3. **費用驅動**：工作量主要來自共用能力只做一次、許多功能需逐一承接、整批套件置換、特殊例外，或跨層整合驗證中的哪一類？使用「逐一承接既有功能」「整批置換不相容套件」等白話即可，不把內部公式塞給客戶。
4. **完成結果**：完成何種建置、部署、回歸、相容或功能驗證，才算這筆工作交付？

功能說明是一條精簡的施工與成果說明，不是內部證據清單，也不是只換名稱的標題。明確屬於客戶採購範圍的 JDK、Spring Boot、Vue、WebLogic 等名稱可直接出現；class、package、API 編號、搜尋命中、內部工作代碼與上游 issue 留在內部分頁。

生成後進行一次 PM 轉述檢查：只把實際交付的五欄主表交給未參與盤點的人，請他說出改造範圍、至少兩個主要動作、白話費用驅動與完成結果。任一項說不出來，就回到案件主檔重寫該列、重新生成，再閱讀新的實際產物。30～220 字只作資訊量診斷，不是文案目標或完成判決；公司歷史報價可用來比較閱讀密度，但不以平均字數倒填內容。

有 sidekick 能力時，將實際生成的 `estimate-external.csv`，以及案件要求時實際 Excel 的對外分頁，交給一個未參與盤點的 fresh reader 作語意 eval；不提供方法卡、預期答案或內部人天公式。reader 逐列回述上述四項，並標出只能重複標題、無法解釋費用的句子。主 Agent 只重寫失敗列、重新生成並重跑同一檢查，不因文案修改改動既有人天。無 sidekick 時，主 Agent 暫時隱藏內部分頁，以相同四問閱讀實際產物完成自審。

這項 eval 是 MOE，因為它直接驗證 PM 的實際說明任務。字數、五欄、公式、revision 與 generator 測試是 MOP：它們確保產物可靠，但不替代上述閱讀結果。通過後直接交付該份已閱讀產物；不另建立 hash、review token 或平行狀態來證明「曾經審過」。

### 真實報價用詞範例

以下樣態取自公司既有的兩份升版報價，已移除客戶與案件識別。它們示範的是對外文字應有的概括程度，不是要求每案照抄版本號或技術選項：

| 系統功能 | 對外功能說明的經典寫法 | 原參考表總人天 |
|---|---|---:|
| 現行程式升級 JDK 21 | 調整新版 JDK 語法、遷移 Jakarta 相容套件、升級 Spring Framework／Spring Boot、置換不相容套件並完成弱點修正與回歸測試 | 65 |
| 環境更新 | 升級 Java 與應用伺服器環境，調整環境變數、配置文件及滲透測試設定 | 30 |
| 帳單業者端－前端開源軟體提升 | 提升 Vue 版本、更換相容第三方套件，並調整因套件升版影響的既有程式 | 39 |
| 帳單業者端－後端開源軟體提升 | 提升 Java 與 Spring Boot、更換 Jakarta 相容套件，並調整既有程式與命名空間 | 58 |
| WebLogic 提升 | 安裝新版 WebLogic、完成測試與正式 Domain 建置，並執行程式部署驗證 | 6 |

`系統功能` 可以保留客戶熟悉的系統區塊與升版成果；`功能說明` 以數個同層級動詞概括「升級、置換、調整、驗證」，並收在一個可確認的完成結果。class、package、API、檔案數、上游 issue 與每個例外的施工方式留在內部分頁。

上表的參考檔只提供總人天，沒有可靠的開發／測試拆分，因此 Skill 不推測原案的拆法。新案件生成正式五欄主表時，`開發人天` 與 `測試人天` 必須是純數字，並由內部 `effortSplit` 各自加總。

### 真實內部細項如何收斂成一列

既有報價中，「帳單業者端－後端開源軟體提升」的 58 人天來自下列細項：

| 內部工作 | 原參考表人天 | 對外歸屬 |
|---|---:|---|
| 開源軟體中風險以上修復 | 10 | 帳單業者端－後端開源軟體提升 |
| Java 8 升級至 Java 17／21 | 5 | 帳單業者端－後端開源軟體提升 |
| Spring Boot 2.7.18 升級至 3.5.16 | 10 | 帳單業者端－後端開源軟體提升 |
| javax 遷移至 jakarta 命名空間 | 9 | 帳單業者端－後端開源軟體提升 |
| 第三方套件 Jakarta 相容置換 | 10 | 帳單業者端－後端開源軟體提升 |
| WebLogic 部署設定調整與驗證 | 5 | 帳單業者端－後端開源軟體提升 |
| 全模組與核心流程回歸、測試報告及資安說明 | 9 | 帳單業者端－後端開源軟體提升 |
| **加總** | **58** | **對外一列** |

新 Skill 延續這種「內部細、對外合併」的結構，並再要求每項內部工作拆出開發／測試人天。產生器依 `clientPackageId` 加總成對外五欄主表，讓 PM 可簡短說明，同時保留工程稽核與重新估算能力。

來源檔案路徑、客戶／專案識別、內網、帳密、原始 log 與內部推理不進外部成果。若內容無法在去識別後仍說明工作價值，先改善工作名稱與根因描述，再生成。

## Excel 格式

Excel 是案件選配。PM 明確需要時，先生成固定 CSV／Markdown／HTML，再由同一個 state revision 建立活頁簿：

1. `對外估算`：唯一的客戶報價主表，只含序號／系統功能／功能說明／開發人天／測試人天。
2. `PM摘要`：方案、總計、責任、包含／排除與重要成立條件；另列每個成果包約 100 字的白話說明，交代 PG 工作、開發／測試人天理由與完成結果。
3. `工作方法`：每個工程工作的方法卡、工作樣態、影響數量、計價理由、完成證據與高值。
4. `內部估算`：低／基準／高、開發／測試拆分、單位費率、乘數、公式與總計。
5. `證據與校準`：依賴／SBOM 重點、來源定位、0 人天項目、未知邊界與歷史類比。

分頁呈現範例：客戶收到或會議投影時先開 `對外估算`；PM 要理解總價或準備向客戶說明時切到 `PM摘要`，逐包閱讀「PG 做什麼／為何是這些開發與測試天數／完成結果」；工程主管追問公式與證據時，再查 `工作方法`、`內部估算` 與 `證據與校準`。成果包短卡是 PM 說明層，不增加對外五欄主表的欄位。

使用 Host 提供的 spreadsheet 能力建立及驗證 Excel；工作簿公式引用同一份明細，不複製手填總數。凍結標題列、啟用篩選、設定合理欄寬與自動換行，並以實際渲染或開啟檢查 PM 摘要可讀性。缺少 spreadsheet 工具時，CSV／Markdown／HTML 仍可交付，並清楚說明未生成 Excel。

Word、PDF 仍是案件選配；使用環境已有的受控轉換工具，保留來源 revision 並做視覺檢查。

## 完成證據

- generator 回報同一 state revision 與各產物 SHA-256。
- internal CSV 公式重算與 state 一致。
- external CSV 的表頭精確等於五個對外欄位，序號皆為數字；每個成果包可追溯到唯一 work item 集合。
- external CSV 每列的功能說明是單段文字；30～220 字作資訊量診斷，最終以「改造範圍／主要動作／費用驅動／完成結果」PM 轉述檢查判定。
- external CSV 的開發＋測試人天等於 internal CSV 的高值總計；兩者都由同一份 `effortSplit` 計算。
- Excel 的對外估算、PM 摘要、工作方法高值與 internal CSV 高值相同；公式、文字標示與快取值不互相矛盾。
- HTML 可在 Chrome 桌面與窄寬度閱讀。
- HTML 每個成果包可用滑鼠與鍵盤展開；頁面、API、檔案標題筆數與逐項清單一致，基準公式可由 state 重算。
- HTML 的主動發現逐項呈現「原本怎麼算／後來查到什麼／所以人天怎麼看／PM 現在要注意什麼」，並留在受影響成果包 dialog。
- HTML 的 direct-touch 工作集合列數等於 `claimedCount`；generated 只說明產製來源、方法、輸出數與核對，不把輸出數渲染成人工逐項清單。
- 每個成果包的圖解具有唯一可存取名稱與描述，所選繪圖工具與資料關係相符。
- 重新執行只改寫列出的 managed outputs，不刪除案件其他檔案。
