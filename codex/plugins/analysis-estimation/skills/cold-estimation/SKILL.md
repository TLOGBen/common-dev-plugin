# 冷啟動估算

目標是用足夠證據完成可討論的初估。使用者要看見做哪些工作、為何需要、如何完成、多少人天及風險條件。以繁體中文交付。

先完整讀本檔與 references/granularity.md、references/rate-card.md、references/checks.md；若輸出截斷，補讀未見部分。描述或搜尋命中不能替代規則正文。續作沿用已確認範圍與證據，只修正受新資訊影響的工作。

## 簡短需求的完整初估

即使使用者只給目標的一句話，也完整執行本 Skill 與適用手冊。路線確認後交付主要工項、具體施工步驟、計算依據與人天；重大路線未決時先依下節 Grilling 交付路線差異與待決問題，不提前詳細定價或宣稱完整初估已完成。只評估、不修改產品或部署發布；產物留在本任務可寫目錄。

既有系統先以保留現有業務與對外契約為暫定範圍，不自行加入業務擴充或另立全面測試專案；是否保留應用架構、核心方案與部署形態，須在開場 Grilling 確認，不能從現況直接推定。路線確認後，目標強制引發的適配及代表性工程驗證照估，必要變更與尚未知責任在報告明示；不得把假設寫成使用者已確認，也不自行假定一次性模組、甲方責任或固定人天。

在使用者已確認的目標、範圍與路線邊界內，自行形成技術推薦；資料不足採明確假設，區分已估與待估。缺正式簽核、一般環境資料或費率不阻擋可成立的初估，但不能用假設代替尚未決定的重大路線。使用者已指定的版本與範圍優先；新證據與其衝突時先說明並確認，不自行換成另一種成果。

依本 Skill 執行獨立定價、撰文及文字校稿；把角色所需手冊與原始工項完整交給指定角色。僅委派 Skill 指定工作，不額外盤點或重估。主模型沿用使用者設定，子代理依手冊指定 profile；載體不支援時依手冊明示退化，不把主線自做稱為獨立結果。

先把完整交付保存成任務產物目錄的 final.md：總結、含施工與完成結果的工項人天表、主導成本施工說明、計算依據與成立條件都在同一份報告；內部稿件連結只供覆核。既有獨立文字 reviewer 同時依 checks.md 檢查交付完整性，主線在最後一次修改後重開實際交付檔核對，不能以數字 token 相同或舊稿 review 完成代替。最後聊天給結論與該完整報告連結。使用者要直接在聊天展開時，使用同一份完整正文；要求其他格式則沿用同一數據轉出。

可用網路查證，使用 Skill 附帶的 inventory.py 或適合的唯讀工具，不安裝建置工具。單一命令或讀取方法失敗時，在既有蒐證預算內換可用方法；仍無證據便記錄限制並交付能成立的部分，不把工具失敗誤當整項評估無法進行。以繁體中文交付。

## 執行方式

主 Agent 在已確認的路線邊界內負責以下三步的技術判斷、工項及最終接受；工時與人天由獨立定價 subagent 提出。其他委派處理會改變主要工項的窄技術疑點，以及已定稿內容的撰文／文字校稿；不另建狀態機或完整審查產線。開始委派或準備交付前，讀 references/pm-delivery.md，依其輸入、角色與停止條件執行。重大路線先依下節確認；一般技術細節與已定範圍內的資料缺口仍以證據及清楚假設處理，不擅自擴大成果。

## 開場先用 Grilling 確認解決方案

重大路線是「採用哪一種解決方案」的選擇，不限於升哪個版本。每次新評估先做足以辨認現況的最小唯讀盤點，立即以 Grilling 確認下列六類適用方案；不能等完成細部相容性研究、工項拆解或定價後才問，也不能只在 AI 自行發現不相容時才問。首輪前只補足辨認現況與說明選項所需的證據，不先研究完所有候選。

逐類辨識「使用者已決定／明確授權」「適用且未決」「不適用」。所有適用且未決的類別都要問，包含本次要沿用升版還是更換方案；現況存在、來源未顯示問題或習慣上會保留，都不算使用者決定。同一決策可覆蓋多類，合併詢問並記錄覆蓋關係；已決或不適用的類別簡短交代即可，不為湊六題重問。若需求中的既有技術實際不存在，先指出前提差異並確認真正成果。

- **應用架構與交付方案**：例如沿用 JSP／ASP.NET 既有伺服器端頁面，或改成現代 SPA 與前後端分離；即使保留業務功能，也會改變畫面施工、API 契約、登入／狀態管理與驗收範圍，不能把一般升版視為已同意這種改造。
- **主要框架**：決定應用結構、請求處理或資料存取模式的框架，例如保留既有框架升版，或移除後改用另一框架。連同施工路線確認：在原專案依 migration guide 適配，或建立目標框架的新骨架、對齊共用能力後搬移既有業務邏輯。核心框架替換或多代耦合改造時，優先評估後者；單純同框架升版仍可採前者，不混算兩條路線。
- **程式語言與主要執行平台**：更換語言、執行期或其世代，牽動既有程式、部署與維護方式。
- **承載關鍵業務功能的核心套件**：例如報表產製引擎，以及實現計價、審批流程、核心查詢或身分驗證的主要套件；改採另一維護線、fork 或產品也屬路線選擇。更換報表引擎或產製方式，即使仍輸出相同檔案格式，也不能只當一般 JAR 升版。
- **實現關鍵處理的基礎設施**：例如資料庫、訊息佇列、交易／批次處理平台、搜尋引擎或應用容器，牽動資料結果、可靠性、部署或維運責任。
- **部署與執行環境變更**：例如客戶不再使用 WebLogic，或改用容器／雲端部署。既有部署描述是現況證據，不等於本次必須保留；已決定離開舊環境，也不等於已選定替代環境。承接已決條件，只詢問尚未決定的替代方案，以及建置、遷移、驗證及維運責任中會改變必要成果或承作範圍的分岔；一般執行配合資料可列條件，不要求四類責任逐項口頭確認才初估，也不把已決的單項責任擴張為全部工作歸屬。

判斷依據是方案承載的能力與候選改變的實作、部署或處理方式，不只看名稱、版本號或檔案數。上述方案即使宣稱 API 相容、修改量小或只有一條推薦路線，仍不能省略未決選擇的確認；技術限制與客戶主動改變方案都適用。其他會改變必要成果、責任邊界或施工量級的分岔也適用；不必先估出兩套人天才判斷是否重大。一般工具套件、已確認維護線內的修補與局部適配，不因資料未齊就觸發。

先查可從原始碼、設定與官方來源取得的事實，給足以理解分岔的現況證據與候選差異，再問使用者決策；尚未查證的候選明示待查，不把全面技術研究當首輪提問的前置。技術上能否沿用由主線查證，不能推給使用者猜；使用者決定必要成果、可接受的改造幅度、部署限制與責任取捨。未驗證不等於不可行；只有一條已知可行路線，若仍改變使用者的成果或限制，也須先確認。

每輪把前提已成立、彼此不依賴未答問題的決策一起編號詢問，各附推薦答案及理由，說清楚選擇會增加、移除或保留哪些工作。依賴本輪答案的問題留待下一輪，不先假定答案展開；不得以未定價的直覺宣稱相差幾倍人天。此處直接遵循這套提問方式，不要求另裝 Grilling 外掛。

存在適用且未決類別時，至少一輪是最低要求；完成條件是上述重大路線選擇已釐清：使用者選定路線，或明確授權 AI 在已確認限制內推薦。所有適用類別已有決策或這項授權，且沒有新衝突時，簡短重述後繼續，不重問；「幫我評估」本身不是授權改選上述方案，也不等於同意全部沿用。授權範圍之外仍須確認。

未決時先交付路線差異、推薦理由與待決問題，在原草稿保存目前證據並明示估算尚未完成。可繼續整理不依賴答案的共用證據與無人天工項；不得為未決路線鎖定基準、交接詳細定價或產生其單一總額。沉默、逾時或只問過一輪都不算答案，也不以蒐證預算或「先交付初估」繞過這個條件。

確認後在原草稿保留使用者決定或授權、採用路線、保留限制與未選路線，再進入詳細工項及定價，不另建狀態機。後續新需求或查證若改變已確認前提，只重新詢問受影響的分岔，沿用其他已成立的證據與工項。

## 本次成果與既有問題的邊界

每個基準工項用一條短因果鏈回答「本次目標改變什麼 → 為何此處需要施工或驗證 → 何種結果代表完成」。來源有舊工具、缺少測試或現有缺陷，並不自動構成本次完整翻新的範圍。沒有目標引發的獨立修改，開發計 0，必要的共享 smoke／代表性回歸仍照計；可能的契約差異先由共用相容處理承接，超出已定範圍的消費端修改列為待定工作，不混入已估總額。

評估工作區的工具版本與缺件不等於產品的目標執行環境。先查既有 CI／部署約定；可沿用的未升版工具鏈，不能因評估機器較新或不相容便收取全面升級費。為本次指定終點必做的建置／容器更新照估。既有問題只有在阻擋本次成果時才列必要修正，否則單獨說明不納入；不能把新發現的所有技術債都算進本次人天。

驗證以變動機制、重要例外和端到端結果形成案例族，同一資料與測試結果能滿足多層條件時只計一次。搬移到新框架時，各搬移頁面、API 與受影響 DAO 方法仍有自己的局部驗證，依 rate-card.md 線性計價；基礎框架測試或少量 smoke 不能代替這些工作。完整業務 UAT 與這些局部驗證、跨功能整合分清責任，明說初估採何種保障程度。

承接使用者已確認的責任與固定額度。已指定由甲方處理的授權、環境建置／穩定性、測試資料、stub、資料遮罩或環境不穩所致重驗，不再列我方工時、風險加價或等待條件；必要應用整合與驗證仍照估。環境配合若有指定固定人天，獨立列一次並先移出既有重疊工時；未拆 E／V 就明列未拆分，不補造分配。

## 蒐證輸出預算

先完成開場的最小盤點與路線確認，再使用下列預算展開細部蒐證；不能先用完預算才開始 Grilling。到界的未知若是未決重大路線，先交付路線差異與問題，不以假設定價。

完整讀 Skill 與手冊不受下列來源輸出上限影響。來源第一輪以最多 12 次有目的的蒐證批次形成初稿，每批可把獨立的計數／定位／少量切片合併在同一命令；之後只為具體缺項補最多 4 批。這是初估蒐證預算，到界仍有未知就寫假設／風險並交付，不為清空未知延長整庫研究。

搜尋先回傳完整計數與少量代表檔名，再讀代表方法及必要例外；每批來源輸出通常控制在 120 行、每行約 300 字元以內。不要直接印全部檔名、全部命中或 minified／vendor 資產。完整統計在工具內計算，輸出摘要與取樣口徑，不能把截斷後的筆數當總量。需要看完整方法才能判断時可補足該方法，明說它要解決哪個工項問題。官方支援查證照做，批次搜尋聚焦高耦合元件；不以輸出預算作為忽略上游風險的理由。

### 1. 清冊後先分流，形成工項草稿

判斷新建、既有改造或混合，承接本次目標差異。程式專案先執行 `python3 scripts/inventory.py <source-root>`（scripts 路徑相對本 Skill），將 Markdown 摘要寫到任務暫存位置並直接讀取；機械處理才加 `--format json`。沿用清冊的 manifest、部署位置、私有成品、import 家族與外部繼承訊號；工具未支援或解析失敗的範圍才手動補查。清冊不是 resolved SBOM、上游支援或執行相容證據。需求文件案直接從需求形成草稿。

把目前證據能支持的主要工項寫進交付草稿：必要性、暫定改法、粗略範圍、驗證結果與未知。接著從這份草稿挑可能改變路線或量級的缺口補查，最後沿用它交付。既有改造以共同機制為工項，沿用業務功能；原始檔案數先作覆蓋證據，依 granularity.md 核實為實際搬移頁面、API 或受影響 DAO 方法後，才作 rate-card.md 的線性乘數。相同規則可共享，逐單位搬移、核對與局部驗證不能被「同質一批」抹掉。

對高耦合且維護落後、支援不明或已有衝突的依賴，若只核對版本、產碼或編譯相容，可能直到整合測試甚至上線後，才發現關鍵查詢、登入、批次或報表無法運作；更難察覺的是程式仍能執行，但資料筆數、群組、排序或輸出內容已改變。

若原維護者沒有提供對應修復，團隊可能被迫自行修補、維護 fork，或改寫受影響能力。此時原先只估的「換版＋一般回歸」無法涵蓋新增施工、資料結果核對與替代路線驗證，導致預算不足、交期延後，甚至必須回退升級、重新安排切換窗口。

因此，先以一個真實用法確認可能失效的前提，以及候選修復是否處理同一問題。選定路線所需的改造與語意驗證直接列入基準；剩餘不確定工作依 rate-card.md 判斷可納入的一般加值或重大異動，不能用大筆風險掩蓋尚未估清楚的施工。

在展開代表程式查證前，先用清冊選出與本次框架／JDK 邊界有關的產碼、資料存取、框架擴充或必要二進位。依實際用途與失效影響選擇，將每項短結論寫在工項草稿旁。查原上游最新正式 release 的版本、發布日期、直接來源與查證日期，對照目標框架／JDK 的世代與維護時間；特定維護線與 fork 分開標示。本案固定舊版本不代表上游停滯；commit、網頁修改或 artifact 上架日期不冒充正式發布。

- **持續跟進目標更新**：預設維護風險低，形成一般適配與代表性驗證工項；已知破壞性改動照列。此分流不等於證明執行相容。
- **更新明顯落後或已有衝突**：發布與目標世代的明顯落差本身就是維護跟進風險。先在草稿保留受影響能力、可能失效的前提及處理方向；年代不自動等於全面替換或固定加成。
- **狀態未知**：寫未知與條件式路線。日期查無不等於停止維護；先形成可估草稿，可能改變主要工項或量級的缺口留給第二步。

### 2. 從草稿缺口決定下一次查證

對可能改變主要工項的元件，先選最可能推翻「升版後仍可沿用」假設的一種實際用法。優先從自訂框架擴充、特殊查詢／聚合、結果轉換、產碼與執行期的銜接尋找線索；這是選樣提示，不是逐類盤點清單。比較哪個用法最依賴目標框架可能改變的執行行為，以一行說明選擇理由；import、設定或產碼入口也可以選，但須指出它如何牽動必須保留的執行結果。接著查：「這種用法在目標下會如何失效，候選修復是否處理了同一種失效？」用失效機制決定搜尋或代表切片；新證據只修正受影響的工項，已成立的部分沿用。

對第一步分流為落後、已有衝突，或未知且影響主要工項的元件，查原維護者／替代修復來源及目標整合者的支援／限制。搜尋實際元件的 maintenance／maintainer／fork／archived 與 integration support，不先鎖原 repository、版本號或 classifier；搜尋摘要只作定位，以官方來源核實。

把結果接回該工項：「必須保留的能力 → 升版可能打破的前提 → 選定處理路線 → 必要施工與語意驗證」。在已確認的路線邊界內，優先選有持續維護、支援既定目標、後續可升版的候選；不能只因局部修補最便宜就先採用，也不能把最新大版本當成目標相容。依第一手證據形成基準並說明前提；其他路線只留決策備註，不混合低高價或累加。若仍涉及未決重大路線，回到 Grilling；已定路線內有限補查仍未知的部分，明列假設及未覆蓋，不假裝已驗證。

若將依據「不支援／不能沿用」排除既有路線或新增重大替代工作，但依據只有預設版本、摘要或間接推論，先依 pm-delivery.md 做一次窄技術覆核，再由主 Agent 決定；不得為了形式而重審所有元件。每個主要工項已能交代必要性、選定改法、粗略範圍、驗證與未覆蓋工作，就交接工項並定價。僅提高版本、日期或數量精度的查證不改變工項。未知支援／授權以假設與實際限制處理，不等待供應商證明；完整 SBOM、目標版建置或外部承諾不是初估前置。預設不安裝套件或建置；只有隔離探針能改變上述工項決策時才執行，一次針對性修正仍無新證據即記錄限制。

### 3. 合併工作、檢查漏項、計算交付

合併草稿的共享施工與案例族，再用畫面、API、外部界接、批次、非功能、建置交付六面檢查具體漏項；沿用契約的界接保留必要驗證。只針對發現的漏項或重複修正相應工項。

先把無人天的工項清單保存為任務產物（可沿用草稿）：穩定 ID、必要性、選定改法、具體施工與驗證操作、共用／批次／獨立例外、計次口徑、代表證據、責任及未知。固定額度仍保留使用者原指定值；主線不先猜其餘工時或總價，也不帶歷史總額給定價者。

讀 references/work-pricing.md，由一個新上下文 subagent 接收完整工項清單並獨立定價，不逐項各派一人。它完整讀 granularity.md 與 rate-card.md，對同一操作只計一次，依步驟形成原始 E／V、計次、一般加值與固定額度，再用工具核對取整和總數。輸出按原 ID 對回工項，保留可重算的明細。沒有完成這次定價交接，就不能把主線自估冒稱獨立定價成果。

主線只接受可追溯且算式一致的價格；發現漏項、重複、責任混淆或工時缺乏操作依據時，向定價者指出具體列並補事實，依 work-pricing.md 有限修正，不私下重估另一套數字。必要工作無法定價就明列待估並交付已估小計。最後锁定工項、路線、人天、責任及已驗證／待確認狀態，再依 pm-delivery.md 交給 writer 與獨立文字 reviewer，不以定價子代理代替這兩個角色。

## 交付

以下完整報告與人天表格式只適用於重大路線已確認的估算。開場或後續仍有未決路線時，先交付現況證據、方案差異、推薦理由與待決問題，明示估算尚未完成；不為符合報告格式補造人天或總額。

預設依前述方式先形成完整 Markdown 報告，聊天提供結論與連結；使用者要求直接展開時交付相同正文。第一塊直接總結：本次主要改動、建議路線、選定路線的總人天及開發／驗證／未拆分固定額度、最重要的成立條件與未定工作。保持精簡，詳細背景與查證過程放在後段。

第二塊直接列工項與人天表：ID、工作、做法與完成結果、執行人天、驗證人天、合計。交付表的 ID 由 1 起連續編號，儲存格只放純數字；Markdown 與 Excel 一致。內部計價 ID 保留於計算明細及對應資料，供核算使用，不混入交付表的 ID 欄。「做法與完成結果」依 pm-delivery.md 的適用句型，用編號短句交代具體施工及驗證，不只寫「相容調整／補回歸」；點數依實際工作，不為湊句型補造施工。第一、二塊之間不插入現況清冊、技術路線長解或證據表。各工項的執行、驗證人天依 rate-card.md 向上取整到整人天，總計加總各列，原始工時留在後段。依共同機制自然合併，保持完整覆蓋，不為壓縮列數混合不同施工或驗收結果。

不另出風險區塊或「基準＋風險」並列表。一般加值併入對應工項，說清楚要完成的處理；已定價的重大異動與固定額度各自是主表工作。採用前提、未選互斥路線、甲方責任與待估事項放在相關列備註。待估不是 0；有必要工作未定價時，只能稱已估小計，不能冒稱全案總額或上限。

主表之後，把主導成本的工作展開成 PM 可讀的施工說明：現況與必要性 → 實際施工 → 共用／批次與例外 → 完成標準，沿用計價草圖，不重新研究。原始工時與代表證據續放後段，供需要時覆核：保留包別／工作、目標差異與改法、代表來源或假設、計價單位與數量、施工步驟及 E／V 小時、人天及完成條件。由同一數列生成主表與明細，不重寫一份不同數字的估算。

需要 Excel 時，在估算完成後以同一組數據產生 `.xlsx`（可用 openpyxl／pandas），不重新盤點或重估。分頁依序為「摘要彙總」與「工項明細」，沿用上述總結與主表，沒有獨立風險頁／區塊。交付的 Excel 不列「原始 E 小時」「原始 V 小時」欄，保留執行／驗證人天；原始小時及換算留在內部計算資料，除非使用者另要求展示。依需要提供內部版與對外版；原基準、低高輸入、中點、20% 分類、重疊移除及證據保留作內部計算依據，對外列工作、完成結果、人天、成立條件與責任邊界。各頁及兩版引用同一數列與 rate-card.md 公式，已估小計與待估不混淆。交付前重開檔案核對公式、總數與可讀性；不能只以匯出成功當作可用。

## Gotchas：容易讓升版初估失準的地方

- **未查整組相容性就預設保留 Struts，漏掉框架替換的大工項。** 「保留既有功能」不等於「既有框架可保留」；即使原需求只寫 Java／Spring 升版，也不能先把 Struts 列為沿用、零改動或僅升 JAR。推薦沿用前，必須找到目標框架、部署容器與整合套件可同時成立的依據；未知只能列待查，不能寫成可保留。必須交叉核對「應用伺服器實際提供的 Servlet／EE 規格、框架最低需求、整合套件與命名空間」。例如 [WebLogic 15.1.1](https://docs.oracle.com/en/middleware/standalone/weblogic-server/15.1.1/notes/whatsnew.html) 提供 Jakarta EE 9.1／Servlet 5.0，而 [Struts 7](https://struts.apache.org/getting-started/how-to-create-a-struts-web-application) 要求 Jakarta Servlet 6 以上；這證明該版本組合不成立，不代表所有 Jakarta 環境都不能保留 Struts。Struts 6 的 javax Web 整合與 Spring 6 的 Jakarta Web 整合也不能只看各自能升版就假定可組合，須查實際版本的依賴與接合點。若容器、Spring 世代及支援要求都固定，既有 Struts 路線又不成立，移除 Struts 的入口、綁定、攔截與回應改造必須明列必要工作，不能只留相容性風險；但改框架或改部署環境屬互斥重大路線，先回 Grilling 確認，再把選定路線估入。不得未經確認就把全部 Action 改寫成 Spring MVC；每案重查官方版本需求，不把此例寫死成永久相容矩陣。
- **把 JSON result 當作沒有 OGNL，或把 Action 數直接當完整重寫數。** `type="json"` 只能證明該回應形式；[Struts JSON plugin](https://struts.apache.org/plugins/json/) 的 `root` 本身可用 OGNL，參數綁定、攔截器及驗證也要查。盤點須涵蓋 include／繼承設定、global result、Convention／註解與直接回應，不能只搜顯式 result type 就宣稱全庫沒有 JSP；沒有 result 的 Action 也須讀方法確認，不能一律當下載。若實證主要是 JSON API，先抽代表請求追到共用 BaseAction、Service 與回應契約，區分可保留的業務邏輯、共用機制一次轉換、同質入口批次適配及串流／上下載等例外；Action mapping、類別與方法分開計數，不把映射筆數逐筆乘完整重寫單價。改寫驗證涵蓋 URL／HTTP 方法、參數與錯誤、權限、JSON 欄位／日期／null，以及例外的串流與標頭，依實際用法縮減或補足。
- **把「好像可行」當基準，卻沒先找明示支援且活躍維護的方案。** 先從候選維護者的官方支援矩陣、migration guide／README 與近期正式 release，找出同時明示支援目標框架／執行期世代、且仍持續維護該路線的候選；官方來源包含替代維護者，不只原始倉庫。滿足本次必要能力與既定限制時，優先採這類有直接依據的方案，不因原套件有新版、classifier 或看似可編譯，就先選它再把關鍵相容性全推給後續驗證。例如 QueryDSL 搭配 Hibernate 6，先比較原維護線與 OpenFeign QueryDSL 的官方支援／遷移說明及正式發布；若後者對目標有明示支援且持續更新，優先列為推薦候選，除非有具體不適用證據或使用者限制；完成路線決定或授權確認後，才作定價基準。以一句話交代「誰明示支援哪個目標、維護依據、為何採用」；未找到就明列未知，不補成好像可行。候選的明示支援不等於本案特殊用法已驗證；再將 GroupBy／transform 等必要適配與代表驗證接成工項，不要求完整實測後才能初估。
- **例如 QueryDSL：換 Jakarta classifier、重產 Q 類，不代表分組查詢能運作。** QueryDSL 5.0.0 曾在已採 Jakarta classifier 的情況下，因 Hibernate 6.1.5 的 `ScrollableResults.get(int)` API 差異，於 `GroupBy／transform` 執行時發生 `NoSuchMethodError`（[原上游案例 #3428](https://github.com/querydsl/querydsl/issues/3428)）。若本案使用這類查詢，先定位並讀到命中的完整方法，再查目標版本及候選修復是否處理同一失效；只看到 import 或檔案開頭不算讀到用法。初估要接成「分組能力必須保留 → 迭代／轉換行為可能失效 → 相容維護線、局部修補或受影響查詢改寫 → 分組、排序、空值與重複列驗證」，將選定相容路線的必要施工估入工項，再依剩餘工作判斷一般加值或重大異動。若修復改成整批載入結果，也需估代表資料量的記憶體驗證。這是選樣與推導工項的例子，不是預設每案必須換 fork；沒有該用法或目標版已修復，就依實證縮減工作。
- **把有新版當成有人維護這條路線。** 最新版可能跟隨另一個框架世代；原維護線失效時，修補、回移植與持續維護責任可能落到承作團隊。確認候選修復是否對應本案的目標與失效。
- **只列相容性風險，沒列失敗後的工作。** 真正需要局部改寫或替代時，原預算可能不足以恢復必要能力，造成延期、追加成本或回退升級。先選可維護的路線，把已知改造估清楚；剩餘不確定工作須對應原工項並通過 20% 分類，不能籠統加一包相容性天數。
- **把所有可能後果都加進基準。** 會把粗估膨脹成全面翻修，還可能重複收取互斥方案。選定路線的已知必做與合格一般加值合併成主表工作；未選替代、甲方責任與範圍外工作不累加。

命中上述情況時，只補足會改變工項或量級的證據；重大路線已確認，且能列出選定工作、驗證、計價依據與待定範圍便交付。Gotchas 的候選優先順序用於推薦，不取代重大路線的使用者決策或授權。
