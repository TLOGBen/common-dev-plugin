# 冷啟動估算

目標是用足夠證據完成可討論的初估。使用者要看見做哪些工作、為何需要、如何完成、多少人天及風險條件。以繁體中文交付。

先完整讀本檔與 references/granularity.md、references/rate-card.md、references/checks.md；若輸出截斷，補讀未見部分。描述或搜尋命中不能替代規則正文。續作沿用已確認範圍與證據，只修正受新資訊影響的工作。

## 執行方式

由主 Agent 完成以下三步，預設不派代理、不另建狀態機或審查文件。缺公司費率、環境或正式責任承諾時，採清楚假設估算；只有無法形成可比較初估的目標歧義才問使用者。使用者指定目標直接採用，其他選擇作推薦路線，不擅自擴大成果。

## 本次成果與既有問題的邊界

每個基準工項用一條短因果鏈回答「本次目標改變什麼 → 為何此處需要施工或驗證 → 何種結果代表完成」。來源有舊工具、缺少測試或現有缺陷，並不自動構成本次完整翻新的範圍。沒有目標引發的獨立修改，開發計 0，必要的共享 smoke／代表性回歸仍照計；可能的契約差異先由共用相容處理承接，未確認的消費端修改列條件增量。

評估工作區的工具版本與缺件不等於產品的目標執行環境。先查既有 CI／部署約定；可沿用的未升版工具鏈，不能因評估機器較新或不相容便收取全面升級費。為本次指定終點必做的建置／容器更新照估。既有問題只有在阻擋本次成果時才列必要修正，否則單獨說明不納入；不能把新發現的所有技術債都算進本次人天。

驗證以變動機制、重要例外和端到端結果形成案例族，同一資料與測試結果能滿足多層條件時只計一次。保留功能不是重建整套測試工程的同義詞；完整逐功能重新驗收與本次改造的代表性工程回歸分清責任，明說初估採何種保障程度。

## 蒐證輸出預算

完整讀 Skill 與手冊不受下列來源輸出上限影響。來源第一輪以最多 12 次有目的的蒐證批次形成初稿，每批可把獨立的計數／定位／少量切片合併在同一命令；之後只為具體缺項補最多 4 批。這是初估蒐證預算，到界仍有未知就寫假設／風險並交付，不為清空未知延長整庫研究。

搜尋先回傳完整計數與少量代表檔名，再讀代表方法及必要例外；每批來源輸出通常控制在 120 行、每行約 300 字元以內。不要直接印全部檔名、全部命中或 minified／vendor 資產。完整統計在工具內計算，輸出摘要與取樣口徑，不能把截斷後的筆數當總量。需要看完整方法才能判断時可補足該方法，明說它要解決哪個工項問題。官方支援查證照做，批次搜尋聚焦高耦合元件；不以輸出預算作為忽略上游風險的理由。

## 程式來源先用清冊工具

來源是程式專案時，先執行 `python3 scripts/inventory.py <source-root>`（scripts 路徑相對本 Skill），把 Markdown 摘要寫到任務暫存位置並直接讀取；不必自行探索 JSON schema（機械處理才加 `--format json`）。這是一輪唯讀掃描：manifest 宣告、部署設定位置、私有成品、程式量、import 家族和外部繼承候選。用它取代手動印全庫檔名、逐 POM 抄依賴及反覆重做相同計數，剩下的蒐證預算用於代表方法、例外和路線判斷。

腳本輸出只代表明示的掃描範圍：不是 resolved SBOM、不是執行相容證據，也不判定上游支援。依 manifest 與實際 import／擴充訊號選出高耦合元件，照上面的維護／整合支援規則查官方來源；不要因取得清冊就跳過這一步。程式語言或建置格式未支援、解析失敗、來源無法讀取時，只針對缺口手動補查；需求文件案直接按需求盤工項，不為使用工具改變案件模式。

## 高耦合元件的先行查證

取得宣告與實際使用訊號後，先完成這個短查證，再深讀業務程式。對有實際使用、跨目標版本邊界的產碼／資料存取整合／外部框架擴充，每個元件執行兩種不同目的的搜尋：

1. `<實際元件名稱> (maintenance OR maintainer OR fork OR archived)`：確認原上游的維護／支援狀態及是否有替代維護來源。
2. `<目標框架名稱> <實際元件名稱> integration support`：確認目標整合者採用的路線、支援承諾與限制。

搜尋詞依實際名稱替換，不用模糊的「最新版相容性」同時回答兩個問題。第一個維護查詢先用實際元件名稱與上述維護意圖，不預先以 site:／domains 鎖住原 repository，也不先加版本號或 classifier；這些限制可能把其他維護來源與整合者的公告排除。找到候選來源後，再回到原上游、目標整合者或替代維護者的第一手文件核實。此規則替代原有維護搜尋，不額外增加查證階段；查無依據仍可帶未知與路線假設交付。優先讀目標框架官方文件與原上游／替代上游的直接公告；搜尋摘要只作定位。即使已知道版本號或 classifier，也不能省略維護目的的搜尋。每項用一句有直接 URL 的主張，或明確的查無證據結論，形成「現況使用 → 支援／維護 → 採用路線 → 工項與風險」。來源並未承諾的支援不能自行補成承諾，未查得不等於停止維護。

此步處理會改變路線的關鍵元件，不擴大成全部套件健康稽核。完成短表後，回到必要工項；未知有清楚路線假設與風險便可交付。

### 1. 先形成工作集合

讀需求／目錄、主要建置與部署設定。判斷新建、既有改造或混合，列出目標差異與候選工作。既有改造先問「哪些共同機制需要改，哪些業務功能能沿用」，不要逐功能重新估建置。

按候選工作找代表原始碼、設定及例外。一次搜尋同類訊號，只回傳計數、檔名及必要切片；避免輸出整庫或反覆掃同一份程式。範圍數量用於覆蓋，施工乘數另外判斷。把證據直接寫進工作表草稿，不等完整盤點報告才開始估算。

### 2. 補查會改變工項的依賴與例外

核對已取得的 manifest、lockfile、私有元件、產碼、部署及 runtime。識別真正使用框架內部 API、產碼、adapter／SPI、跨大版本或有維護疑慮的元件。對這些元件查現行官方來源：原維護者與支援狀態、原路線及替代路線、與目標框架的耦合。版本號或編譯可過不等於受支援或執行語意一致。


每個會改變路線的元件用短結論保留「實際用法 → 上游支援證據／未知 → 採用路線 → 一次性改造、驗證及後續維護責任」。上游停滯或缺支援時，採有條件的保留／替代／自行維護路線形成初估，額外適配和語意驗證列實際工作。不能只寫相容性待確認。

再看畫面、API、外部界接、批次、非功能、建置交付六面有無遺漏。沿用契約的界接仍需驗證；不用把所有既有契約重新施工。

只在結果會改變採用路線、施工乘數或風險量級時補查。初估不以完整 SBOM、目標版建置或外部承諾為前置條件。預設不安裝整套套件或執行建置；若靜態證據不足且探針能改變上述決策才做隔離探針。一次有針對性的修正仍無新證據便記錄限制，继续估算。

### 3. 計算、一次覆核、交付

按 rate-card.md 用實際施工步驟估工時，工具加總。對照六面覆蓋、共享工作、例外與風險做一次覆核；只補會改變答案的具體漏項或重複，修正後核對受影響列。主要工作已有改法、估價依據與風險條件就交付，不為流程完整重盤來源。

## 交付

預設聊天 Markdown；要求檔案時只產生需要的內部明細與對外版，同一組數據生成。先說總人天、包含的開發／驗證／普通風險、成立條件，再給工項表。

內部每列：包別／工作、目標差異與改法、代表來源或假設、計價單位與數量、施工步驟及工時、執行與驗證人天、完成條件。可把步驟理由放表後，避免超寬表格。

對外每列：工作、做法與完成結果、執行人天、驗證人天、合計。必要的依賴路線與風險不能因簡化而消失。附具體風險的觸發、額外工作與人天區間，以及含風險總額；替代路線互斥列示。無法界定部分列未覆蓋與原因，不能把已估小計稱全案上限。

表後精簡列來源限制、未驗證事項、未納入的責任、持續維護與覆核修正。不要用流程宣告或列數代替工作品質。
