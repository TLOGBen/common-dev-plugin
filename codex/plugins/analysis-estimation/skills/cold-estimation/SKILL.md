# 冷啟動估算

目標是用足夠證據完成可討論的初估。使用者要看見做哪些工作、為何需要、如何完成、多少人天及風險條件。以繁體中文交付。

先完整讀本檔與 references/granularity.md、references/rate-card.md、references/checks.md；若輸出截斷，補讀未見部分。描述或搜尋命中不能替代規則正文。續作沿用已確認範圍與證據，只修正受新資訊影響的工作。

## 執行方式

主 Agent 負責以下三步的範圍、技術路線、工項及最終接受；工時與人天由獨立定價 subagent 提出。其他委派只處理會改變主要工項的窄技術疑點，以及已定稿內容的撰文／文字校稿；不另建狀態機或完整審查產線。開始委派或準備交付前，讀 references/pm-delivery.md，依其輸入、角色與停止條件執行。缺公司費率、環境或正式責任承諾時，採清楚假設估算；只有無法形成可比較初估的目標歧義才問使用者。使用者指定目標直接採用，其他選擇作推薦路線，不擅自擴大成果。

## 本次成果與既有問題的邊界

每個基準工項用一條短因果鏈回答「本次目標改變什麼 → 為何此處需要施工或驗證 → 何種結果代表完成」。來源有舊工具、缺少測試或現有缺陷，並不自動構成本次完整翻新的範圍。沒有目標引發的獨立修改，開發計 0，必要的共享 smoke／代表性回歸仍照計；可能的契約差異先由共用相容處理承接，超出已定範圍的消費端修改列為待定工作，不混入已估總額。

評估工作區的工具版本與缺件不等於產品的目標執行環境。先查既有 CI／部署約定；可沿用的未升版工具鏈，不能因評估機器較新或不相容便收取全面升級費。為本次指定終點必做的建置／容器更新照估。既有問題只有在阻擋本次成果時才列必要修正，否則單獨說明不納入；不能把新發現的所有技術債都算進本次人天。

驗證以變動機制、重要例外和端到端結果形成案例族，同一資料與測試結果能滿足多層條件時只計一次。保留功能不是重建整套測試工程的同義詞；完整逐功能重新驗收與本次改造的代表性工程回歸分清責任，明說初估採何種保障程度。

承接使用者已確認的責任與固定額度。已指定由甲方處理的授權、環境建置／穩定性、測試資料、stub、資料遮罩或環境不穩所致重驗，不再列我方工時、風險加價或等待條件；必要應用整合與驗證仍照估。環境配合若有指定固定人天，獨立列一次並先移出既有重疊工時；未拆 E／V 就明列未拆分，不補造分配。

## 蒐證輸出預算

完整讀 Skill 與手冊不受下列來源輸出上限影響。來源第一輪以最多 12 次有目的的蒐證批次形成初稿，每批可把獨立的計數／定位／少量切片合併在同一命令；之後只為具體缺項補最多 4 批。這是初估蒐證預算，到界仍有未知就寫假設／風險並交付，不為清空未知延長整庫研究。

搜尋先回傳完整計數與少量代表檔名，再讀代表方法及必要例外；每批來源輸出通常控制在 120 行、每行約 300 字元以內。不要直接印全部檔名、全部命中或 minified／vendor 資產。完整統計在工具內計算，輸出摘要與取樣口徑，不能把截斷後的筆數當總量。需要看完整方法才能判断時可補足該方法，明說它要解決哪個工項問題。官方支援查證照做，批次搜尋聚焦高耦合元件；不以輸出預算作為忽略上游風險的理由。

### 1. 清冊後先分流，形成工項草稿

判斷新建、既有改造或混合，承接本次目標差異。程式專案先執行 `python3 scripts/inventory.py <source-root>`（scripts 路徑相對本 Skill），將 Markdown 摘要寫到任務暫存位置並直接讀取；機械處理才加 `--format json`。沿用清冊的 manifest、部署位置、私有成品、import 家族與外部繼承訊號；工具未支援或解析失敗的範圍才手動補查。清冊不是 resolved SBOM、上游支援或執行相容證據。需求文件案直接從需求形成草稿。

盤點元件時，於「前置需求／後置影響」條列其官方預設支援或配套的元件版本；未明示則標未知。

清冊後先把目前證據能支持的主要工項寫進交付草稿：必要性、暫定改法、粗略範圍、驗證結果與未知。接著從這份草稿挑可能改變路線或量級的缺口補查，最後沿用它交付。既有改造以共同機制為工項，沿用業務功能；來源數量用於覆蓋，施工乘數另外判斷。

對高耦合且維護落後、支援不明或已有衝突的依賴，若只核對版本、產碼或編譯相容，可能直到整合測試甚至上線後，才發現關鍵查詢、登入、批次或報表無法運作；更難察覺的是程式仍能執行，但資料筆數、群組、排序或輸出內容已改變。

若原維護者沒有提供對應修復，團隊可能被迫自行修補、維護 fork，或改寫受影響能力。此時原先只估的「換版＋一般回歸」無法涵蓋新增施工、資料結果核對與替代路線驗證，導致預算不足、交期延後，甚至必須回退升級、重新安排切換窗口。

因此，先以一個真實用法確認可能失效的前提，以及候選修復是否處理同一問題。選定路線所需的改造與語意驗證直接列入基準；剩餘不確定工作依 rate-card.md 判斷可納入的一般加值或重大異動，不能用大筆風險掩蓋尚未估清楚的施工。

在展開代表程式查證前，先用清冊選出與本次框架／JDK 邊界有關的產碼、資料存取、框架擴充或必要二進位。依實際用途與失效影響選擇，將每項短結論寫在工項草稿旁。查原上游最新正式 release 的版本、發布日期、直接來源與查證日期，對照目標框架／JDK 的世代與維護時間；特定維護線與 fork 分開標示。本案固定舊版本不代表上游停滯；commit、網頁修改或 artifact 上架日期不冒充正式發布。

- **持續跟進目標更新**：預設維護風險低，形成一般適配與代表性驗證工項；已知破壞性改動照列。此分流不等於證明執行相容。
- **更新明顯落後或已有衝突**：發布與目標世代的明顯落差本身就是維護跟進風險。先在草稿保留受影響能力、可能失效的前提及處理方向；年代不自動等於全面替換或固定加成。
- **狀態未知**：寫未知與條件式路線。日期查無不等於停止維護；先形成可估草稿，可能改變主要工項或量級的缺口留給第二步。

### 2. 從草稿缺口決定下一次查證

對可能改變主要工項的元件，先選最可能推翻「升版後仍可沿用」假設的一種實際用法。優先從自訂框架擴充、特殊查詢／聚合、結果轉換、產碼與執行期的銜接尋找線索；這是選樣提示，不是逐類盤點清單。比較哪個用法最依賴目標框架可能改變的執行行為，以一行說明選擇理由；import、設定或產碼入口也可以選，但須指出它如何牽動必須保留的執行結果。接著查：「這種用法在目標下會如何失效，候選修復是否處理了同一種失效？」用失效機制決定搜尋或代表切片；新證據只修正受影響的工項，已成立的部分沿用。

對第一步分流為落後、已有衝突，或未知且影響主要工項的元件，查原維護者／替代修復來源及目標整合者的支援／限制。搜尋實際元件的 maintenance／maintainer／fork／archived 與 integration support，不先鎖原 repository、版本號或 classifier；搜尋摘要只作定位，以官方來源核實。

把結果接回該工項：「必須保留的能力 → 升版可能打破的前提 → 選定處理路線 → 必要施工與語意驗證」。互斥方案優先選有持續維護、支援既定目標、後續可升版的路線；不能只因局部修補最便宜就先採用，也不能把最新大版本當成目標相容。依第一手證據選一路形成基準並說明前提；其他路線只留決策備註，不混合低高價或累加。有限補查仍無法選路線時明列假設及未覆蓋，不假裝已定版。

若將依據「不支援／不能沿用」排除既有路線或新增重大替代工作，但依據只有預設版本、摘要或間接推論，先依 pm-delivery.md 做一次窄技術覆核，再由主 Agent 決定；不得為了形式而重審所有元件。每個主要工項已能交代必要性、選定改法、粗略範圍、驗證與未覆蓋工作，就交接工項並定價。僅提高版本、日期或數量精度的查證不改變工項。未知支援／授權以假設與實際限制處理，不等待供應商證明；完整 SBOM、目標版建置或外部承諾不是初估前置。預設不安裝套件或建置；只有隔離探針能改變上述工項決策時才執行，一次針對性修正仍無新證據即記錄限制。

### 3. 合併工作、檢查漏項、計算交付

合併草稿的共享施工與案例族，再用畫面、API、外部界接、批次、非功能、建置交付六面檢查具體漏項；沿用契約的界接保留必要驗證。只針對發現的漏項或重複修正相應工項。

先把無人天的工項清單保存為任務產物（可沿用草稿）：穩定 ID、必要性、選定改法、具體施工與驗證操作、共用／批次／獨立例外、計次口徑、代表證據、責任及未知。固定額度仍保留使用者原指定值；主線不先猜其餘工時或總價，也不帶歷史總額給定價者。

讀 references/work-pricing.md，由一個新上下文 subagent 接收完整工項清單並獨立定價，不逐項各派一人。它完整讀 granularity.md 與 rate-card.md，對同一操作只計一次，依步驟形成原始 E／V、計次、一般加值與固定額度，再用工具核對取整和總數。輸出按原 ID 對回工項，保留可重算的明細。沒有完成這次定價交接，就不能把主線自估冒稱獨立定價成果。

主線只接受可追溯且算式一致的價格；發現漏項、重複、責任混淆或工時缺乏操作依據時，向定價者指出具體列並補事實，依 work-pricing.md 有限修正，不私下重估另一套數字。必要工作無法定價就明列待估並交付已估小計。最後锁定工項、路線、人天、責任及已驗證／待確認狀態，再依 pm-delivery.md 交給 writer 與獨立文字 reviewer，不以定價子代理代替這兩個角色。

## 交付

預設聊天 Markdown；要求檔案時把完整交付寫在同一份報告，聊天只給結論與連結。第一塊直接總結：本次主要改動、建議路線、選定路線的總人天及開發／驗證／未拆分固定額度、最重要的成立條件與未定工作。保持精簡，詳細背景與查證過程放在後段。

第二塊直接列工項與人天表：ID、工作、做法與完成結果、執行人天、驗證人天、合計。交付表的 ID 由 1 起連續編號，儲存格只放純數字；Markdown 與 Excel 一致。內部計價 ID 保留於計算明細及對應資料，供核算使用，不混入交付表的 ID 欄。「做法與完成結果」依 pm-delivery.md 的適用句型，用編號短句交代具體施工及驗證，不只寫「相容調整／補回歸」；點數依實際工作，不為湊句型補造施工。第一、二塊之間不插入現況清冊、技術路線長解或證據表。各工項的執行、驗證人天依 rate-card.md 向上取整到整人天，總計加總各列，原始工時留在後段。依共同機制自然合併，保持完整覆蓋，不為壓縮列數混合不同施工或驗收結果。

不另出風險區塊或「基準＋風險」並列表。一般加值併入對應工項，說清楚要完成的處理；已定價的重大異動與固定額度各自是主表工作。採用前提、未選互斥路線、甲方責任與待估事項放在相關列備註。待估不是 0；有必要工作未定價時，只能稱已估小計，不能冒稱全案總額或上限。

主表之後，把主導成本的工作展開成 PM 可讀的施工說明：現況與必要性 → 實際施工 → 共用／批次與例外 → 完成標準，沿用計價草圖，不重新研究。原始工時與代表證據續放後段，供需要時覆核：保留包別／工作、目標差異與改法、代表來源或假設、計價單位與數量、施工步驟及 E／V 小時、人天及完成條件。由同一數列生成主表與明細，不重寫一份不同數字的估算。

最後精簡列來源限制、未驗證事項、未納入責任、持續維護與覆核修正。不要用流程宣告或列數代替工作品質。

需要 Excel 時，在估算完成後以同一組數據產生 `.xlsx`（可用 openpyxl／pandas），不重新盤點或重估。分頁依序為「摘要彙總」與「工項明細」，沿用上述總結與主表，沒有獨立風險頁／區塊。交付的 Excel 不列「原始 E 小時」「原始 V 小時」欄，保留執行／驗證人天；原始小時及換算留在內部計算資料，除非使用者另要求展示。依需要提供內部版與對外版；原基準、低高輸入、中點、20% 分類、重疊移除及證據保留作內部計算依據，對外列工作、完成結果、人天、成立條件與責任邊界。各頁及兩版引用同一數列與 rate-card.md 公式，已估小計與待估不混淆。交付前重開檔案核對公式、總數與可讀性；不能只以匯出成功當作可用。

## Gotchas：容易讓升版初估失準的地方

- **例如 QueryDSL：換 Jakarta classifier、重產 Q 類，不代表分組查詢能運作。** QueryDSL 5.0.0 曾在已採 Jakarta classifier 的情況下，因 Hibernate 6.1.5 的 `ScrollableResults.get(int)` API 差異，於 `GroupBy／transform` 執行時發生 `NoSuchMethodError`（[原上游案例 #3428](https://github.com/querydsl/querydsl/issues/3428)）。若本案使用這類查詢，先定位並讀到命中的完整方法，再查目標版本及候選修復是否處理同一失效；只看到 import 或檔案開頭不算讀到用法。初估要接成「分組能力必須保留 → 迭代／轉換行為可能失效 → 相容維護線、局部修補或受影響查詢改寫 → 分組、排序、空值與重複列驗證」，將選定相容路線的必要施工估入工項，再依剩餘工作判斷一般加值或重大異動。若修復改成整批載入結果，也需估代表資料量的記憶體驗證。這是選樣與推導工項的例子，不是預設每案必須換 fork；沒有該用法或目標版已修復，就依實證縮減工作。
- **把有新版當成有人維護這條路線。** 最新版可能跟隨另一個框架世代；原維護線失效時，修補、回移植與持續維護責任可能落到承作團隊。確認候選修復是否對應本案的目標與失效。
- **只列相容性風險，沒列失敗後的工作。** 真正需要局部改寫或替代時，原預算可能不足以恢復必要能力，造成延期、追加成本或回退升級。先選可維護的路線，把已知改造估清楚；剩餘不確定工作須對應原工項並通過 20% 分類，不能籠統加一包相容性天數。
- **把所有可能後果都加進基準。** 會把粗估膨脹成全面翻修，還可能重複收取互斥方案。選定路線的已知必做與合格一般加值合併成主表工作；未選替代、甲方責任與範圍外工作不累加。

命中上述情況時，只補足會改變工項或量級的證據；能列出選定工作、驗證、計價依據與待定範圍便交付。
