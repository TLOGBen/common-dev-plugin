# 窄覆核、PM 工作說明與最終驗證

主 Agent 在使用者已確認的範圍與重大路線邊界內決定技術做法，並接受獨立定價的結果。委派不能重啟完整初估，也不能接觸未授權的產品修改。一次委派只交付一個明確結果；提供精確可讀來源與可寫產物範圍，禁止再派代理。使用者指定模型／effort 優先；Codex 可用時，撰文使用 gpt-5.6-terra / low，窄技術覆核使用 gpt-5.6-terra / medium。這兩個角色無法委派時可由主線明示退化處理，不假稱獨立結果。交付前的最終 reviewer 必須另開新上下文並固定 gpt-5.6-terra / medium（Terra Mid；使用者另有明確指定才變更），不能由 writer、定價者或主線自審代替。若無法固定此 profile、工具失敗或未取得覆核結果，保留待覆核草稿並明示原因，不能宣稱最終驗證通過；不為取得模型而安裝工具。

## 決策前的窄覆核（有觸發才做）

- 技術：準備排除可沿用路線或新增重大替代，但關鍵依據只是預設版本、摘要或間接推論時，交付待判斷主張、既定目標、實際用法、候選改動與直接來源。派工時原文附上這項判定規則：

  > 只覆核這個會改變工項的主張。先區分「舊路線已知失敗」與「候選改動後仍會失敗」。若候選改動會切換設定、adapter、handler、實作或呼叫方式，沿一條代表用法確認改動後實際選到的實作與失敗點是否仍可到達，再判支持／反證／未知。舊失敗程式碼仍存在、預設版本不同或尚未完成完整驗證，都不足以反證候選改動。反證要指出改動後仍成立的失敗鏈；未知則列一個最小驗證與對應工項，不能改寫成禁止沿用。這只核對一條承重因果鏈，不重查全套供應鏈或要求完整產品驗證；最多三項發現，附直接來源及限定語。

主 Agent 依發現判斷候選可行性；若涉及 SKILL.md 定義的未決重大路線，先交付 Grilling 問題，不能以技術覆核代替使用者的選擇或授權。候選能避開某個失敗不等於整體相容或持續維護已獲證明；仍保留已選路線必要的代表驗證。

技術覆核至多一次，把相關疑點合併；收到發現後只補受影響的證據或工項。摘要須保留會改變判斷的限定語與直接來源，不能把「未找到」「可能」「僅預設版本」壓成確定事實。來源全文留在原處，主線只針對負責決策的疑點回讀，不回收整庫搜尋輸出。已定路線仍缺技術證據時保留條件式初估；重大路線未決則先交付路線差異與待決問題，不提前定價。

## 定價後的撰文與獨立最終覆核

1. 主 Agent 鎖定工項 ID、選定版本／路線、數字、責任、具體操作與完成標準，包含已證實／推估／待確認狀態。提供原表及主導成本的施工草圖，不要求為寫作另做一份冗長狀態文件。
2. Writer 完整讀 SKILL.md 的「交付」與 checks.md，再依鎖定原表、工項草圖及同一版本的定價明細組裝完整報告；不得只照輸入簡表省略規定欄位，也不能把表內的「做法與完成結果」移到後文章節就視為已滿足。只改工作名稱、說明及施工段落的表達，數字與計算明細由既有資料忠實帶入。一次處理全稿，使用下列適用句型；不得查網路、讀產品程式、改價格或增加工作。原始數字與事實不足時把該處標回主 Agent，不自行補想像。
3. Writer 完成後，另開不繼承主線歷史的新上下文 Terra Mid reviewer（支援 fork_turns 的載體用 none）。它完整讀本節、checks.md、granularity.md、rate-card.md 與 SKILL.md 的「交付」，再讀實際 final.md、已確認目標／路線／責任、無人天工項與施工草圖、接受版本的 input.json／result.json／pricing.md，以及原清單直接指向的代表程式、設定與官方依據。不可只給報告摘要或主線的 PASS 結論；不要帶入希望達到的總人天、其他輪結果或要求支持原判斷。
4. Reviewer 依下節覆核三個實質面向，同時檢查文字、表格與計算依據。只讀報告、定價資料及產品來源，僅在指定位置寫覆核結果；不直接改報告、價格、產品或另派代理。主線依發現修正表達與結構；工項／技術問題由主線回原證據處理，人天問題帶受影響 ID、具體操作與來源交原定價者，沿用 work-pricing.md 的有限修正規則。涉及改變已確認重大路線時回 Grilling，不藉 reviewer 擴張授權。
5. 修正後交同一 reviewer 核對受影響內容及其跨列合計、共享歸屬和結論，不重跑全套盤點或另一輪獨立估價。每次補查須能解決具體發現；仍缺關鍵證據就保留問題，不換 reviewer 或反覆改寫以取得 PASS。覆核完成後，主線最後一次寫入再依 checks.md 用工具重開實際交付檔，核對六欄、ID 對應、逐列 E／V／合計與計算明細。任何改動都核對受影響內容；路線、施工方式、數字、責任或成立條件有實質改變，必須再次取得 reviewer 對新版本的結論，不能套用舊稿 PASS。純排版或同義改寫由主線核對差異與數據未變，保留與覆核版本的對應；轉出 Excel 等格式另做轉檔後檢查。

### Terra Mid 最終驗證的三個面向

每個主表工項都核對下列對應；深入回讀聚焦於決定路線能否成立的依賴與主導成本的實際改法。先沿用已交付證據，只有具體矛盾或足以推翻結論的缺口才補讀代表用法及必要的官方第一手來源；不展開全庫研究、完整建置、供應鏈審計或重新估算。

| 面向 | 必須核對的實質內容 |
|---|---|
| 方案可行性 | 必須保留的能力、選定版本／維護線、執行期、容器規格與整合方式能否同時成立；從實際用法連到目標改法及完成結果。區分官方支援、編譯／產碼可用與執行語意已驗證，不能互相冒充；原路線的失敗也不能直接反證已改變接線的候選方案。 |
| 前後一致性 | 總結、主表、施工說明、計算明細、責任及待估是否同一版本、同一路線；有無互斥方案混用、保留能力卻漏必要改造、假設變成承諾、同一工作既計費又宣稱排除、必要待估移出主表，或已估小計冒稱全案總額。 |
| 人天與實際改法匹配 | 對回「代表現況 → 可重用的轉換／實作方式 → 本列剩餘操作 → 次數及原始 E／V 工時 → 人天 → 完成標準」。檢查共用一次、批次、例外與產碼是否按實際工作計價；批次 N／N₀ 口徑及基準工時是否一致、有無重乘本案數量、固定費／跨層結果重收、抽樣驗證卻收全量逐支重做工時。主導成本須有能解釋時間的操作與反覆次數；不能只因公式算對、數字沒變或總額看起來合理就通過，也不憑直覺壓價或倒推目標總額。 |

### 覆核結果與交付條件

覆核結果保存在原任務產物，記錄實際 reviewer 呼叫的 model／effort、代理識別、受審報告及定價資料版本／雜湊；工具未提供的執行資訊明示不可確認。每個面向分別回傳 PASS、NEEDS_FIX 或 UNVERIFIED，附直接來源與主表 ID／段落；每項問題說明「衝突或缺口 → 對可行性／施工／人天的影響 → 最小修正或補證」。同時回報主表列數、逐欄合計、計算明細位置與未解事項，不能只寫已校稿或數字相同。

三個面向與 checks.md 均通過，且沒有足以推翻選定路線、必要工項或主要人天依據的未解問題，才可宣稱最終覆核完成。已明示且不影響已估部分成立的一般環境條件、尚未實測與待估工作，可保留為條件式初估；reviewer 須明確限定通過的範圍，PASS 不代表產品已升版、全案已定價或所有執行結果已驗證。存在上述實質缺口或 reviewer 未完成時，只能交付「待覆核草稿／已估小計」與具體問題，不能包裝成通過驗證的最終報告。

## 三類句型（取實際適用動作，不套出新工項）

每列先寫清楚工作名稱，再以編號短句說明具體操作及完成結果，通常三至五點；簡單工作可少於三點。以 PM 能向客戶說明「為何需要、做什麼、完成後可保留什麼」為準，不設硬字數上限。三類是寫法，不是額外計價分類。下列括號由已定事實填入，未提供的施工不得照抄。

| 類型 | 名稱句型 | 施工說明句型 |
|---|---|---|
| 框架升版 | 【系統／服務】升版至【已選框架與版本】 | 1. 因【本次目標差異】調整【啟動／共用設定】。<br>2. 處理【實際受影響 API／命名空間】的相容差異。<br>3. 調整【已判定需改的共用請求或排程處理】。<br>4. 以【代表 API／排程／啟動紀錄】確認【預期結果】。 |
| 一般套件升版 | 【套件用途】相容版本調整 | 1. 改用配合【既定目標】的【已選相容版本／維護線】。<br>2. 調整【既有呼叫／設定】。<br>3. 處理【已確認必要的格式或輸出差異】，沿用【既有內容】。<br>4. 比對【代表輸出或功能結果】。 |
| 關鍵核心升版 | 【核心能力】相容處理與結果確認 | 1. 因【已知或可能失效前提】調整實際受影響的【設定、程式或產物】。<br>2. 依【已選處理路線】適配【既有特殊用法】。<br>3. 區分【共用／批次處理】與【需獨立處理的例外】。<br>4. 以【關鍵情境及代表資料】確認【必須維持的結果】。 |

替代方案句型：主 Agent 已確認維護狀態並選定替代路線時，寫「【A】已停止維護，改採【B】的轉換方案，調整【既有呼叫／設定／產碼】，並以【代表情境】確認【必須保留的結果】。」若已知的只是目標相容限制，改寫為「【A】不支援【既定目標】」；未確認停止維護就保留未知，不以版本較舊代替證據。沿用主 Agent 已選的方案與施工，writer 不自行選替代品或增加工項。

例如已確認有 QueryDSL 分組／結果轉換用法時，可說「調整產碼設定並重產供查詢使用的 Q 類；依已選相容路線處理可能受跨代迭代 API 差異影響的分組與結果轉換；比對分組、排序、空值及重複列。若修復需整批載入資料，再驗證代表資料量的記憶體使用。」實際用法與處理路線須由主 Agent 的證據提供，不預設所有核心元件都有產碼，也不預設每案都需換 fork。

主表後以主導成本的施工草圖展開：現況與必要性 → 實際施工 → 共用／批次與例外 → 完成標準。保留工程意思，首次出現的縮寫補短用途；別把具體說明縮成「相容調整、補回歸」。驗證是計畫而非已完成，通用未實測狀態說一次，各列保留特有條件。沿用不改則說明必要驗證歸屬，不重收。這些寫法同樣適用 Excel 說明欄，數字引用同一份估算資料。
