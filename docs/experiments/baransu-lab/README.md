## 這次實驗什麼

核心假設：同一份清楚、可反駁的驗收記錄，能讓「判斷 → 釘清成果 → 獨立檢視 → 完成驗收」沿用已知決策與證據，不必每跨一個 skill 就重開問題、重寫合約或重跑完整流程。這是假設，不是已證明的效率或品質提升。

| 入口 | 大膽刪掉 | 保留下來 |
|---|---|---|
| lab-think | 固定三輪問答、已清楚選擇的重複確認、調查前全面禁用工具 | 人的價值與授權決策、根據證據做建議、可推翻條件 |
| lab-contract | 強制根目錄 CONTRACT.md、一頁硬上限、指定實作手法、自動歸檔 | 可否決壞結果的條件、真實前提、精確常數、相鄰獨立條件 |
| lab-review | 自動修 typo／格式、固定五視角、固定 HTML 日誌 | 純審查不異動、獨立新上下文、具體觸發條件與因果證據 |
| lab-seal | 每次完整 suite、固定五點重挖、stable sealed 標記與 hook 遙測 | 獨立驗證、真實路徑、零測試層不豁免、修後針對性複驗 |

## 一份記錄怎麼用

有現成且適用的驗收條件就沿用；沒有時，使用 .baransu-lab/acceptance/<task>.md。它記錄成果與範圍、前提證據、可觀察條件、必要常數及實質修正。既有決策和授權有效，不為了流程再問一次。

獨立驗證後另存一張 .baransu-lab/receipts/ 收據，連回同一份驗收記錄與實際工件身分。這張收據只說明「哪些條件被什麼證據支持」，不宣稱全系統正確。

修正前提也不能連帶放掉鄰近條件。例如資料來源待釐清，不代表廠商篩選、日期傳遞、權限範圍都暫停驗收；有第一手證據證明原前提錯誤，也不能只按舊文字否決正確修正。

## 仍然會停的地方

- 必須由人決定的價值、範圍或授權未定。
- 只有審查／驗證授權卻需要改碼；嚴重程度不會自動產生修改權。
- 必要證據或獨立 verifier 不可用；不能寫成獨立通過。
- 不知道被驗證的確切工件，或驗證後工件又改變。

原 Baransu 的 Stop hook 不認這個實驗收據。本包不寫原封緘標記、不補造 hook 遙測，也不自動 ship、歸檔、刪除或改外部狀態。若你的環境要求原流程封緘，仍需另走原流程；本包不繞過它。

## 比較基準與限制

設計時分別閱讀隔壁 Baransu 儲存庫的 5.0.0 Claude 來源，以及已安裝 5.4.1 Codex 快取的 think、contract、review、seal。兩者不同：較新快取已有 finding 品質檢查、影響分級、probe admission 與較窄複驗。本實驗吸收其重要意圖，不宣稱是 5.4.1 的官方升級，也沒有修改原十四個技能。

隔壁來源的對照 commit 是 ad8a88b16830f3c7963d93ef888dbb30898109cf；設計完成後再查，該工作樹仍乾淨。

初版 0.1.0 已完成獨立 Codex 導出、暫存安裝與 8 次初步 A/B 回應測試；證據入口見[共同說明](../README.md)與[實測發現](../common-lab/RESULTS.md)。它們不等於實際產品封緘或真人理解。行數減少不等於實際 token 節省，也不代表品質已提高。

實戰請對照同一任務的必要停頓、無謂停頓、已完成條件、漏抓缺陷、錯誤阻擋、時間與平台實際 token。沒有平台遙測的項目寫「不可取得」，不要用文字長度估算實際用量。
