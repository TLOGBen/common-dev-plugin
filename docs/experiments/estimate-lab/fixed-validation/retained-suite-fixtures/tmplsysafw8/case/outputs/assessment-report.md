#### 修改明細

##### 建立共用承接底座

PG 會先建立新版應用共同使用的啟動、輸入輸出與登入狀態設定，再用一個代表入口確認共用行為正確。這項工作只做一次，不會按四支入口重複計價；完成後新版應用應可建置、啟動，並讓後續功能共用同一套承接方式。

- 影響頁面（0）：不涉及
- 影響 API（1）：共用應用啟動與 Session 契約
- 對應檔案（2）：src/main/resources/application.yml、src/main/java/app/config/WebConfig.java
- 落點說明：本項建立共用底座，不直接修改個別業務頁面。
- 基準公式：1 × 4.0 = 4.0 人天
- 基準理由：基準值以一位工程師完成共用設定、啟動排錯與主要契約核對所需的正常工期估算；不按入口數重複收費。

### 既有功能入口可延續使用｜低 1.5／基準 3.0／高 4.5 人天

逐支調整既有功能入口、參數與回應承接方式，核對原網址及操作契約，並完成代表性功能回歸驗證。

處理方式：將 3 支入口逐支接回新底座並核對行為。

#### 修改明細

##### 接回需要處理的功能入口（共 4 支／需處理 3 支）

PG 會逐支核對三個受影響入口的網址、輸入參數、回應內容與錯誤處理，再接到新版共用底座。工作量按三支計算，因為每支都要獨立理解與驗證；完成後使用者仍可沿用原網址與操作方式，代表入口的正常與失敗情境都要通過。

- 影響頁面（2）：查詢首頁、資料維護頁
- 影響 API（3）：GET /legacy/search、POST /legacy/save、POST /legacy/approve
- 對應檔案（3）：src/main/java/app/web/SearchAction.java、src/main/java/app/web/SaveAction.java、src/main/java/app/web/ApproveAction.java
- 落點說明：四支入口中一支已由新底座承接，不需修改。
- 基準公式：3 × 1.0 = 3.0 人天
- 基準理由：每支基準 1 天，包含讀懂原參數、接回新底座、處理一輪例外並完成局部驗證；三支各有自己的輸入輸出，因此以三支計價。
