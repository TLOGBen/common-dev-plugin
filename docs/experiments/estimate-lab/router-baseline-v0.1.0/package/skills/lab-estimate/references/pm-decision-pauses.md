# PM 決策停等指南

當案件準備要求 PM 回答、要判斷某個 gate 是否需要停等，或決策問題看起來像技術問卷時讀取。

## 停等的目的

停等是把案件的承諾權交還給 PM。Agent 已先承擔技術查證，現在需要 PM 決定客戶要買到的成果、願意承擔的成本與風險、責任如何分配，或要購買哪一層驗收保障。

一個真正需要 PM 的停等同時符合三個條件：

1. 不同答案會實質改變成果、範圍、方案、人天、責任、契約、部署、生命週期或驗收保障。
2. PM 能以客戶成果與交付語言理解並作答；技術推導已由 Agent 完成。
3. 聊天已提供足以區分選項的決策包。

只表示 Agent 進度、技術事實仍待查證，或下一步可由證據直接決定的 gate，是進度投影。Agent 更新案件狀態後繼續處理 Frontier。使用者先前已明確回答的事項，Agent 以白話回述並寫入決策紀錄，讓 gate 自然完成。

## 一張合格的決策包

每次 `currentDecision.requiresHuman: true` 都要讓 PM 在一則可快速閱讀的聊天訊息中看懂：

1. **現在要決定什麼**：一句客戶成果或責任語言的問題。
2. **為什麼需要 PM**：指出這項選擇形成哪個承諾，以及為何技術證據不能代替人類決定。
3. **作決定所需的事實**：只放能區分選項的現況、已知限制與數量；來源與技術細節可展開。
4. **每個選項買到什麼**：分別說明成果、成本特性、主要風險、責任／前置條件、長期影響與驗收差異。
5. **Agent 的建議**：清楚標示推薦與理由，也說明推薦成立的條件。推薦保持為建議，直到 PM 選定。
6. **哪些可以稍後決定**：把尚未影響目前方向的選項延後，避免一次要求 PM 承擔過多認知。
7. **決定後會發生什麼**：說明 Agent 將展開的盤點、排除的路線、需重算的範圍或下一個決策點。
8. **其他（自行輸入）**：允許 PM 描述新的成果方向、組合選項或補充限制；Agent 先回述理解，再重組後續分析。

### 第一次就解釋方案語言

方案名稱是閱讀索引，不是完整說明。只要名稱含有可能被不同人解讀成不同做法的詞，決策包就在選項第一次出現時一併回答：

1. 這句話用白話是什麼意思？
2. 開發期間依什麼順序前進，每段用什麼結果檢查？
3. 正式交付是一次或多次；過渡層、中間版本或雙軌是否會保留？
4. 它和另一個最相近方案的實質差異是什麼？
5. 這個差異如何改變成本、風險、時程或維護責任？

若順序本身就是方案價值，使用簡短 ASCII 流程圖。例：「分段直達」應直接說成「開發與驗證分段進行，正式只交付一個最終版本；中間相容層在交付前移除」，並畫出現況、各檢查點與最終版本。這段說明出現在選案問題之前，使 PM 的第一次答案就是知情選擇。

選項彼此代表可辨識的客戶結果。後端框架、Java、前端工具、資料層與部署環境等獨立升版軸分開呈現，只有相依證據證明必須綁定時才組成同一選項。若證據只支持一條可行路線，決策改成「是否接受這組成果、條件與保障」，而不是製造形式上的替代方案。

## 決策從哪裡回答

Estimate V3 以目前聊天作為 PM 決策入口。Agent 在聊天呈現決策包；PM 回答後，Agent 寫回案件主檔並自動推進到下一個真正的停等點。Host 授權與工具 approval 使用 Host 原生介面，和 PM 的成果／方案／人天決策分開。

## Agent 與 PM 的分工

Agent 先自行查明：

- 實際版本、依賴、classpath、私有 JAR、產碼鏈與容器契約。
- 頁面、route、Action／Controller、API、batch、界接、DAO 與 SQL 的實際足跡。
- 可否建置、啟動、部署或以代表性 probe 證明的技術事實。
- 重複計數、批次可轉換樣態、真正例外及未知邊界。

PM 決定：

- 客戶這次要解到哪一層，以及哪些技術線納入成果。
- 哪一個經證據支持的方案成為對外承諾。
- 我方、客戶 IT 與第三方的責任，以及環境施工是否計入。
- 驗證深度、成立條件、排除事項與可接受風險。
- 最終工作內容與對外人天是否可交付。

技術上可行只代表一個選項存在；它不會自動成為 PM 的選擇。資料不足時，Agent 先找高價值證據；只有該資料屬於 PM／客戶持有且不同答案會改變承諾時，才把它轉成 PM 決策。

## 六個 gate 的承諾意義

| Gate | PM 真正要形成的承諾 | 何時停等 | Agent 先準備什麼 |
|---|---|---|---|
| 1 提供案件資料 | 案件對象、初始目標與可使用的資料／權限正確 | 仍缺少足以建立案件的身分、目標或資料授權 | 回述已收到的案件資料、目的與可安全執行的盤點方式 |
| 2 選擇成果大方向與工作分工 | 客戶這次要買到哪一層成果；環境、UAT、壓測與第三方工作由誰承擔 | 有兩種以上會改變後續探索範圍的成果方向，或責任尚未形成承諾 | 最小現況證據、獨立升版軸、每個方向的成果／成本特性／風險／保留內容與推薦 |
| 3 核對案件理解 | 成果、保留行為、範圍、責任與驗收語意符合客戶需求 | 誤解會使後續方案或估算重做 | 一頁白話摘要；數量與技術清單放在次要層 |
| 4 選擇採用方案 | 從已證明可落地的成功路徑中選一條 | 候選方案在成果、成本、風險、責任或生命週期上有實質差異 | 每案成功條件、地圖、成本區間、主要風險、外部前置、優缺點與推薦 |
| 5 確認工作內容與人天 | 對外承諾包含哪些工作、驗證深度與保守人天 | 工作切片、人天或驗收保障需要 PM 核准 | 逐包約 100 字說明 PG 工作、量級依據、開發／測試理由與完成結果；再呈現算法、包含／排除、低／基準／高意義及對外高值 |
| 6 取得交付成果 | 交付目的地、格式或正式發布方式需要確認時才形成承諾 | 只有交付方式或發布責任仍待選擇時 | 可下載成果、revision、品質檢查與接續方式；一般情況作為完成狀態而非停等 |

### Gate 5 先解釋，再請 PM 核准

總人天表只能告訴 PM「多少」，不足以讓他判斷「這筆錢買到什麼」。詢問 PM 是否確認總人天之前，先逐一說明每個客戶成果包：

- 標題直接顯示成果包名稱及 `開發 X／測試 Y`。
- 約 100 字白話說明 PG 實際要做什麼、主要數量或例外為何形成此量級、開發與測試各保障什麼，以及做到什麼算完成。
- 低／基準／高只需在逐包說明後統一解釋；PM 核准的是對外高值與其範圍，不必在每張卡內重複三組數字。
- 技術證據、完整公式與逐檔清單放在可追溯的內部文件；聊天保留 PM 做出承諾所需的資訊。

這段的 MOE 是：PM 看完後能逐包回答「PG 要做什麼、為何開發／測試各需要這些天、完成後得到什麼」，再決定是否接受總價。卡片數量、字數範圍與欄位齊全只是讓這個結果可穩定重現的 MOP。

## 停等前的自我檢查

在把 `currentDecision` 設成需要人類回答前，Agent 逐項確認：

- 我能否用唯讀證據自行得到答案？若可以，先查證。
- 這個答案會改變客戶承諾嗎？若不會，列為資訊或進度。
- PM 看完是否知道自己要做什麼、為什麼值得花時間？
- 選項是否都有相稱的資訊，能公平比較？
- 推薦是否清楚標示，且案件狀態仍保持未選？
- 「其他」輸入是否真的能改寫方向，而非被硬套回最近的預設選項？
- PM 回答後，Agent 的下一步是否明確且能自動接續？

這個檢查決定「現在是否值得停」。它保存人的承諾權，也讓 Agent 在其餘時間持續推進，而不是把每個未知都轉交給 PM。
